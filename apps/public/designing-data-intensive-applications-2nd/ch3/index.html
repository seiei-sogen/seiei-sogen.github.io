3章の入口

データモデルは層になっている

データモデルとは、データの「形」の決め方です。表にするのか、入れ子のJSONにするのか、点と線にするのか。

本は、データモデルを「ソフトウェア開発でおそらく最も重要な要素」と言います。コードの書き方だけでなく、問題の考え方そのものを変えてしまうからです。

アプリは、データモデルを何段も重ねて作られています。どの段でも問いは同じです。「これを、1つ下の段でどう表現するか？」

この章で比べるモデルは5つです。あるモデルで簡単なことが、別のモデルではぎこちなくなります。だから「いつどれを使うか」を知っておく価値があります。

先に覚える言葉：宣言型クエリ言語

この章に出てくるクエリ言語（SQL、Cypher、SPARQL、Datalog）は、ほとんどが宣言型です。

定食屋で考えます。「サバ味噌定食ください」と言うのが宣言型です。欲しいものだけ伝えて、作り方は厨房に任せます。厨房に入って「まず鍋に水を入れて」と手順を指図するのが、PythonやJavaのような普通のプログラミングです。

宣言型
何が欲しいかを書く
  • 結果が満たす条件と、並べ替えや集約のしかたを書く
  • どのインデックスを使うか、どの順で実行するかは、DBのクエリオプティマイザが決める
命令型
どうやるかを書く
  • どの操作をどの順でやるか、アルゴリズムを自分で書く
  • 速くしたければ、自分で書き直す

宣言型がうれしい理由は3つあります。

  • 短い。アルゴリズムを書くより簡潔です。
  • DBが勝手に速くなれる。実装の中身が隠れているので、クエリを1文字も変えずにDB側が性能を改善できます。
  • 並列化もDB任せ。複数のCPUコアやマシンで並列に実行する方法を、自分で考えなくて済みます。
3.1

リレーショナルモデルとドキュメントモデル

ひとことで言うと

木の形のデータはドキュメント、つながりの多いデータはリレーショナル。いまのDBはだいたい両方できる。

いちばん有名なデータモデルは、SQLが使っているリレーショナルモデルです。1970年にEdgar Coddが提案しました。

リレーション＝SQLのテーブル
データを入れる表。
タプル＝SQLの行
表の1行。リレーションは、タプルの「順序のない集まり」です。

このモデルには、50年のあいだ何度も挑戦者が現れました。そして毎回、リレーショナルが生き残りました。

  1. 1970年Coddがリレーショナルモデルを提案。最初は「本当に効率よく作れるのか」と疑われた。
  2. 1970年代〜80年代前半ネットワークモデルと階層モデルが対抗。リレーショナルが圧倒。
  3. 1980年代半ばRDBMSとSQLが定番の道具になる。
  4. 1980年代後半〜90年代前半オブジェクトデータベースが登場。定着せず。
  5. 2000年代前半XMLデータベースが登場。ニッチ止まり。
  6. 2010年代NoSQLとNewSQL。言葉としては薄れたが、ドキュメントモデルという置き土産を残した。
  7. いまSQLのほうがXML、JSON、グラフを取り込んで成長している。

NoSQLが残したドキュメントモデルは、データをふつうJSONで表します。MongoDBやCouchbaseが広め、いまではほとんどのRDBもJSONを扱えます。この節は、この2つのモデルの比べっこです。

3.1.1 オブジェクトとテーブルは形が合わない

アプリのコードの中では、データは入れ子のオブジェクトです。DBの中では、平たい表です。形が違うので、あいだに不格好な変換層が要ります。

このズレをインピーダンスミスマッチと呼びます。電子工学から借りた言葉で、回路同士のインピーダンスが合わないと信号が反射してしまう、という話が元です。

ORMは変換を楽にするが、万能ではない

ActiveRecordやHibernateのようなORMは、この変換のための決まりきったコードを減らしてくれます。ただし批判も多い道具です。

困るところ
  • 2つのモデルの違いを隠しきれない。結局、両方を考えることになる
  • ほぼOLTP専用。分析する人は生のテーブルを触るので、スキーマ設計はやはり大事
  • 検索エンジン、グラフDB、NoSQLには対応が弱い
  • 自動生成されたスキーマは、使いにくく非効率なことがある
  • 非効率なクエリを気づかずに書いてしまう（N+1問題）
助かるところ
  • 単純で繰り返しの多い変換コードが減る
  • クエリ結果のキャッシュで、DBの負荷を下げられるものもある
  • スキーマのマイグレーションなど、管理作業を手伝ってくれる

N+1クエリ問題は図で見るとすぐわかります。コメントをN件表示するページで、投稿者の名前も出したいとします。

一対多のデータは、ドキュメントのほうが自然

本は履歴書（LinkedInのプロフィール）を例にします。名前は1人に1つです。でも職歴や学歴は、1人が複数持ちます。これが一対多の関係です。

リレーショナルで素直に作ると、テーブルが4つに分かれます。子テーブルは user_id で親を指します。

同じ情報を、JSONのドキュメント1個で書くとこうなります。

{
  "user_id": 251,
  "first_name": "Barack",
  "last_name": "Obama",
  "region_id": "us:91",
  "positions": [
    {"job_title": "President",
     "organization": "United States of America"},
    {"job_title": "US Senator (D-IL)",
     "organization": "United States Senate"}
  ],
  "education": [
    {"school_name": "Harvard University",
     "start": 1988, "end": 1991},
    {"school_name": "Columbia University",
     "start": 1981, "end": 1983}
  ],
  "contact_info": {"website": "https://barackobama.com"}
}

一対多の関係は、データの中に木の形を作ります。JSONはその木をそのまま書けます。

JSON版のいいところは局所性です。関連する情報が1か所にまとまっているので、1回読めば全部そろいます。クエリも速くて単純です。

補足

「一対多」は本当は「一対少数」

履歴書の職歴は、せいぜい数件です。だから埋め込めます。有名人の投稿につくコメントのように数千件あるものを、1つのドキュメントに全部埋め込むのは無理があります。その場合はテーブルを分けるリレーショナル方式のほうが向いています。

3.1.2 正規化、非正規化、結合

さっきのJSONで、地域は "us:91" というIDでした。なぜ「Washington, DC」と文字で書かないのでしょう。

地域の一覧を別に用意して、そこから選ばせる形にすると、いいことが5つあります。

  • 表記がそろう。書き方やスペルがバラバラになりません。
  • あいまいさが消える。「Washington」が首都なのか州なのか、迷いません。
  • 直すのが楽。名前は1か所にしかないので、都市名が変わっても一発です。
  • 翻訳できる。一覧を翻訳しておけば、見る人の言語で表示できます。
  • 検索が賢くなる。「ワシントンは東海岸」という知識を一覧に持たせれば、「東海岸の人」で検索できます。

IDは人間にとって意味がないので、変える必要がありません。指している中身が変わっても、IDはそのままです。逆に、意味のある文字をあちこちに複製すると、変更のたびに全部のコピーを直すことになります。直し漏れれば不整合です。

正規化にも代償があります。画面に出すたびに、IDを人間が読める文字に引き直す必要があります。リレーショナルでは、これを結合（JOIN）でやります。

SELECT users.*, regions.region_name
FROM users
JOIN regions ON users.region_id = regions.id
WHERE users.id = 251;

ドキュメントDBは、正規化したデータも入れられます。でも非正規化と結びつけて語られがちです。JSONは複製したフィールドを足しやすく、しかも結合の機能が弱いDBが多いからです。

結合がまったくないDBでは、アプリ側で2回クエリを投げます。MongoDBなら、集約パイプラインの $lookup で結合できます。

db.users.aggregate([
  { $match: { _id: 251 } },
  { $lookup: {
      from: "regions",
      localField: "region_id",
      foreignField: "_id",
      as: "region"
  } }
])

正規化のトレードオフ

正規化非正規化
書き込み速い。コピーは1つ高くつく。コピーを全部直す
読み取り遅め。結合が要る速い。結合が少ない
ディスク少ない多い
不整合起きにくい直し漏れの危険
向く場面OLTP、小〜中規模分析、超大規模の読み取り

非正規化は、1章で出てきた導出データの一種だと考えるとわかりやすいです。元のデータからコピーを作っているので、コピーを更新し続ける仕組みが要ります。

更新の途中でプロセスが落ちたらどうなるか、も考える必要があります。アトミックなトランザクション（8章）があれば楽ですが、複数ドキュメントにまたがる原子性を持たないDBもあります。ストリーム処理（12章）で整合性を保つ手もあります。

Xのタイムラインは、実は「半分だけ」非正規化

2章のケーススタディを思い出してください。ホームタイムラインは、posts と follows の結合が高すぎるので、結果を事前に計算してキャッシュしていました。これは非正規化です。

ところが、X（旧Twitter）の実装では、このキャッシュに投稿の本文が入っていません。入っているのは投稿IDと投稿者のIDだけです。

IDだけにする理由は単純です。いいね数は毎秒変わります。アイコンを頻繁に変える人もいます。そんなものをタイムラインに複製しても、すぐ古くなるだけです。容量も大きく増えます。

この例の教訓

読むときに結合があっても、速くてスケールするサービスは作れます。ハイドレーションは並列化しやすく、コストがフォロー数やフォロワー数に左右されないからです。

正規化と非正規化は、良い悪いではありません。読みと書きの速さ、作る手間のトレードオフです。一部だけ非正規化して残りは正規化のまま、という組み合わせが最善のこともあります。判断するときは、情報がどれくらい頻繁に変わるか、読み書きのコストがどうなるかを見ます。

3.1.3 多対一と多対多

関係には3種類あります。

いまの履歴書では、勤務先や学校名はただの文字列でした。これを「組織」というエンティティにして、IDで指すようにするとどうなるでしょう。ロゴを載せたいとき、文字列方式だと全員のプロフィールにロゴURLを複製することになります。エンティティ方式なら、ロゴは組織に1回だけ書けば済みます。

すると関係は多対多になります。1人は複数の組織で働き、1つの組織には複数の人がいるからです。リレーショナルでは、これを関連テーブル（結合テーブル）で表します。

多対一や多対多は、自己完結したJSON 1個にはうまく収まりません。ドキュメントモデルでやるなら、組織は別のドキュメントにして、IDで参照します。

{
  "user_id": 251,
  "first_name": "Barack",
  "last_name": "Obama",
  "positions": [
    {"start": 2009, "end": 2017,
     "job_title": "President", "org_id": 513},
    {"start": 2005, "end": 2008,
     "job_title": "US Senator (D-IL)", "org_id": 514}
  ]
}

多対多は、両方向から引きたくなる

「この人が働いた組織は？」と「この組織で働いた人は？」の両方を聞きたくなります。

  • 両側にIDを持つ。履歴書に組織IDを、組織に履歴書IDを書きます。同じ関係を2か所に書くので非正規化です。食い違う危険があります。
  • 1か所に持ってインデックスで引く。正規化して、セカンダリインデックス（4章）で両方向から速く引けるようにします。リレーショナルなら positions の user_id と org_id の両方にインデックスを張ります。

ドキュメントモデルでも、配列の中の org_id にインデックスを張れるDBは多いです。

3.1.4 スターとスノーフレーク：分析のためのスキーマ

ここは分析の話です。データウェアハウスはふつうリレーショナルで、テーブルの組み方に定番があります。代表がスタースキーマです。本の例は食料品チェーンの売上です。

ファクトテーブル真ん中
1行が1つの出来事です。売上なら1回の購入、Webなら1回のページビューやクリック。あとで自由に分析できるよう、まとめずに1件ずつ記録します。だから巨大になります。大企業では数ペタバイトにもなります。
ディメンションテーブルまわり
その出来事の「誰が、何を、どこで、いつ、どのように、なぜ」を表します。ファクトテーブルから外部キーで指します。

ファクトテーブルのカラムは2種類です。売値や仕入れ値のような属性と、ディメンションへの外部キーです。

日付までディメンションにするのは、「祝日かどうか」のような追加情報を持たせるためです。そうすれば祝日とそれ以外の売上を比べられます。

テーブルは横にとても広くなります。ファクトテーブルは100カラムを超えることが多く、ディメンションも広いです。店舗なら、ベーカリーがあるか、床面積、開業日、最寄りの幹線道路までの距離など、分析に使えそうな情報を全部載せます。

変種：スノーフレークとOne Big Table

  • スノーフレークスキーマ。ディメンションをさらにサブディメンションに分けます。たとえば商品テーブルが、ブランドやカテゴリを文字列で持たずに外部キーで指します。スターより正規化されていますが、アナリストにはスターのほうが扱いやすいので、スターが好まれがちです。
  • One Big Table（OBT）。ディメンションテーブルをなくして、全部をファクトテーブルのカラムに畳み込みます。結合を事前に済ませておくようなものです。容量は食いますが、クエリが速くなることがあります。

分析では、こういう非正規化があまり問題になりません。データは「過去に起きたことの記録」で、基本的に変わらないからです。OLTPで怖かった不整合や書き込みの重さが、ここでは切実ではありません。

ちなみにスターやスノーフレークは、ほぼ多対一の関係でできています。1回の買い物で3品買っても、「まとめ買い」という関係は表しません。商品ごとに別の行を作り、たまたま顧客ID、店舗ID、時刻が同じ、という形にします。

3.1.5 どのモデルをいつ使うか

ドキュメントの強み
  • スキーマが柔軟
  • 局所性のおかげで速い
  • アプリのオブジェクトの形に近いことがある
リレーショナルの強み
  • 結合が得意
  • 多対一、多対多の関係をうまく扱える
  • 木の形なら、無理に分割しない。ドキュメント的な構造を複数テーブルにバラすことをシュレッディングと呼びます。面倒なスキーマと、必要以上に複雑なコードになりがちです。
  • 入れ子の中身は、外から直接指せない。ドキュメントでは「ユーザー251の職歴の2番目」のような言い方になります。直接参照したいなら、どの項目にもIDがあるリレーショナルが向きます。
  • 並べ替えできるリストは、ドキュメントが楽。ToDoのドラッグ&ドロップは、JSON配列に順番どおり入れるだけです。RDBには標準の方法がありません。整数カラムで並べる（途中に入れると番号の振り直し）、IDのリンクドリスト、小数インデックス法（fractional indexing）などの工夫が要ります。

スキーマの柔軟性：「スキーマレス」は言いすぎ

ドキュメントDBは、入れるデータの形を強制しません。好きなキーを足せます。だから「スキーマレス」と呼ばれますが、本はこれを誤解を招く言い方だと言います。

データを読むコードは、結局なにかの形を前提にしているからです。スキーマは「ない」のではなく、「DBが強制していない」だけです。

違いがはっきり出るのは、データの形を変えたいときです。氏名を1つのフィールドに入れていたのを、名と姓に分けたくなったとします。

ドキュメントDB：新しい形で書き始めて、読む側で古い形に対応する

if (user && user.name && !user.first_name) {
  // 古いドキュメントには first_name がない
  user.first_name = user.name.split(" ")[0];
}

RDB：マイグレーションで全行を新しい形にそろえる

ALTER TABLE users
  ADD COLUMN first_name text DEFAULT NULL;

UPDATE users
  SET first_name = split_part(name, ' ', 1);
-- ↑ PostgreSQLの場合
  • ドキュメント方式の弱点は、DBを読むすべての場所が、ずっと昔に書かれた古い形にも対応し続けなければならないことです。
  • RDB方式の弱点は重さです。デフォルト値つきのカラム追加は大きなテーブルでも速いですが、UPDATE は全行を書き換えるので遅くなります。カラムの型変更などは、テーブル全体のコピーが必要になるのが普通です。
  • 無停止でスキーマを変えるツールはいろいろあります。それでも大規模DBでは運用が難しいままです。逃げ道として、カラムを NULL で足すだけにして、読むときに値を補う手もあります。ドキュメントDBと同じやり方です。

スキーマオンリードが向くのは、中身がバラバラなときです。

  • オブジェクトの種類が多すぎて、種類ごとにテーブルを作るのが現実的でない。
  • データの形を外部のシステムが決めていて、いつ変わるかこちらでは制御できない。

逆に、全レコードが同じ形のはずなら、スキーマは形を文書化して守らせる便利な仕組みです。

局所性：まとめて読むなら速い

ドキュメントは、JSONやXML、またはそのバイナリ版（MongoDBのBSONなど）の、ひと続きの文字列として保存されます。

ただし、この利点が効くのはドキュメントの大部分を同時に使うときだけです。

  • DBはふつうドキュメント全体をロードします。大きなドキュメントの一部だけ欲しいときは無駄です。
  • 更新するときも、ふつう全体を書き直します。

なので、ドキュメントは小さめに保ち、こまごました更新を頻繁にしないのがおすすめとされます。

なお、局所性はドキュメントモデルだけの特権ではありません。GoogleのSpannerは、子テーブルの行を親テーブルの中に入れ子にして置けます。Oracleにも似た機能があります。BigtableやHBaseのカラムファミリーも、局所性を管理するための仕組みです。

ドキュメントのためのクエリ言語

RDBはだいたいSQLで聞きます。ドキュメントDBはバラバラです。主キーで出し入れできるだけのもの、セカンダリインデックスがあるもの、立派なクエリ言語を持つものがあります。

XMLにはXQueryやXPath、JSONにはJSON PointerやJSONPathがあります。MongoDBの集約パイプラインも、その仲間です。

本の例は海洋生物学者です。「月ごとに、サメを何匹見たか」を出します。

PostgreSQL

SELECT
  date_trunc('month', observation_timestamp)
    AS observation_month,
  sum(num_animals) AS total_animals
FROM observations
WHERE family = 'Sharks'
GROUP BY observation_month;

MongoDBの集約パイプライン

db.observations.aggregate([
  { $match: { family: "Sharks" } },
  { $group: {
      _id: {
        year:  { $year:  "$observationTimestamp" },
        month: { $month: "$observationTimestamp" }
      },
      totalAnimals: { $sum: "$numAnimals" }
  } }
]);

やっていることは同じです。サメだけに絞り、月でまとめ、数を合計します。集約パイプラインの表現力はSQLの一部と同じくらいで、書き方が英文風かJSON風かの違いです。本は「好みの問題かもしれない」と言います。

2つのモデルは近づいている

これは開発者にとって良いニュースです。ドキュメント側にも他のドキュメントへの参照は要りますし、リレーショナル側にもスキーマをゆるくしたい場所はあります。同じDBで両方を混ぜられるときが、いちばんうまくいきます。

豆知識

Coddは最初から入れ子を認めていた

1970年の最初の論文は、行の中の値が「入れ子のテーブル」であってもよいとしていました。Coddはこれを非単純ドメインと呼びました。30年以上あとにSQLへ入ったJSONサポートと、ほぼ同じ発想です。

3.2

グラフ型データモデル

ひとことで言うと

何でも何にでもつながるデータは、点と線で持つ。「何段先まであるかわからない」たどり方が得意。

モデルの向き不向きは、関係の種類で決まります。

グラフの部品は2種類だけです。

頂点vertex ／ ノード ／ エンティティ
点。人、場所、ページなど「もの」を表します。
辺edge ／ リレーションシップ ／ アーク
線。もの同士の関係を表します。
例頂点辺よく使う計算
ソーシャルグラフ人知り合い
WebグラフページリンクPageRankで人気度を出す
道路・鉄道交差点道路、路線最短経路を探す

グラフの持ち方には、大きく2通りあります。

グラフのもう1つの強みは、種類の違うものを1つに入れられることです。Facebookは、人、場所、イベント、チェックイン、コメントを全部1つのグラフで持っています。検索エンジンのナレッジグラフや、Wikidataも同じ発想です。

この節で見るのは、モデル2つと言語4つです。

  • トリプルストアDatomic、AllegroGraph、Blazegraph

例はずっと同じものを使います。アイダホ出身のLucyと、フランスのサン・ロー出身のAlain。2人は結婚して、ロンドンに住んでいます。

3.2.1 プロパティグラフ

頂点が持つもの
  • 一意なID
  • ラベル（種類を表す文字列）
  • 出ていく辺の集合
  • 入ってくる辺の集合
  • プロパティ（キーと値）
辺が持つもの
  • 一意なID
  • 始点（テール頂点）
  • 終点（ヘッド頂点）
  • ラベル（関係の種類）
  • プロパティ（キーと値）

中身は、リレーショナルのテーブル2枚で表せます。頂点用と辺用です。

CREATE TABLE vertices (
  vertex_id  integer PRIMARY KEY,
  label      text,
  properties jsonb
);

CREATE TABLE edges (
  edge_id     integer PRIMARY KEY,
  tail_vertex integer REFERENCES vertices,
  head_vertex integer REFERENCES vertices,
  label       text,
  properties  jsonb
);

-- 前にも後ろにもたどれるよう、両方に索引
CREATE INDEX edges_tails ON edges (tail_vertex);
CREATE INDEX edges_heads ON edges (head_vertex);

このモデルの大事な性質は3つです。

  1. どの頂点も、どの頂点とでもつなげる。「この種類とこの種類しかつながない」と縛るスキーマがありません。
  2. 前にも後ろにもたどれる。ある頂点から、出ていく辺も入ってくる辺も速く見つかります。これが走査です。
  3. ラベルで種類を分けられる。いろいろな情報を1つのグラフに入れても、ごちゃごちゃになりません。

edges テーブルは、3.1.3の関連テーブルを一般化したものと言えます。あらゆる種類の関係を、1枚のテーブルに入れられるようにしたわけです。

補足

辺が結べるのは2つの頂点だけ

関連テーブルなら、1行に外部キーを3つ持たせて「3者の関係」を表せます。グラフでこれをやるには、その関係自体を表す頂点を1つ足して、そこへ辺を張ります。または、ハイパーグラフという別の仕組みを使います。

グラフは柔軟です。さっきの図にも、普通のテーブル設計では面倒なことが入っています。国によって地域の区切り方が違う。国の中に国がある。Lucyの住所は市まであるのに、出生地は州までしかない。グラフならどれも素直に書けます。

あとから広げるのも楽です。たとえば食物アレルギーを足したければ、アレルゲンの頂点を作り、人から辺を張ります。食品とアレルゲンもつなげば、「この人が安全に食べられるもの」を聞けるようになります。

3.2.2 Cypherクエリ言語

Cypherは、プロパティグラフのためのクエリ言語です。Neo4jのために作られ、いまはopenCypherというオープンな標準になっています。名前は映画『マトリックス』の登場人物からで、暗号のcipherとは関係ありません。

Cypherは、グラフを文字の絵で書きます。

データを入れるときはこう書きます。usa や idaho は、クエリの中だけで使う仮の名前です。

CREATE
  (namerica :Location {name:'North America', type:'continent'}),
  (usa      :Location {name:'United States', type:'country'}),
  (idaho    :Location {name:'Idaho',         type:'state'}),
  (lucy     :Person   {name:'Lucy'}),
  (idaho) -[:WITHIN]-> (usa) -[:WITHIN]-> (namerica),
  (lucy)  -[:BORN_IN]-> (idaho)

では質問です。「アメリカで生まれて、いまヨーロッパに住んでいる人の名前は？」

MATCH
  (person) -[:BORN_IN]->  () -[:WITHIN*0..]->
           (:Location {name:'United States'}),
  (person) -[:LIVES_IN]-> () -[:WITHIN*0..]->
           (:Location {name:'Europe'})
RETURN person.name

肝は *0.. です。「WITHIN の辺を0回以上たどる」という意味で、正規表現の * と同じ感覚です。生まれた場所が州でも市でも、何段か上にアメリカがあればマッチします。

Cypherは宣言型なので、どう探すかは書いていません。全員を1人ずつ調べてもいいし、アメリカとヨーロッパの頂点から逆向きにたどってもいい。どちらが速いかはDBが決めます。

3.2.3 同じことをSQLでやると

グラフはテーブル2枚に入るのだから、SQLでも聞けるはずです。答えは「できるが、つらい」です。

グラフの辺を1本たどることは、edges テーブルとの結合1回にあたります。普通のSQLは、何回結合するかを書く時点で決めます。ところがグラフでは、何本たどるかが事前にわかりません。

SQLでは、再帰共通テーブル式（WITH RECURSIVE）を使います。骨組みはこうです。

WITH RECURSIVE
  -- アメリカの中にある場所を全部集める
  in_usa(vertex_id) AS (
    SELECT vertex_id FROM vertices
     WHERE label = 'Location'
       AND properties->>'name' = 'United States'
    UNION
    SELECT edges.tail_vertex FROM edges
      JOIN in_usa  -- 自分自身を参照＝再帰
        ON edges.head_vertex = in_usa.vertex_id
     WHERE edges.label = 'within'
  ),
  in_europe(vertex_id) AS ( /* 同じ形 */ ),
  born_in_usa(vertex_id) AS ( /* in_usa に born_in で入る人 */ ),
  lives_in_europe(vertex_id) AS ( /* in_europe に lives_in で入る人 */ )
SELECT vertices.properties->>'name'
  FROM vertices
  JOIN born_in_usa     ON vertices.vertex_id = born_in_usa.vertex_id
  JOIN lives_in_europe ON vertices.vertex_id = lives_in_europe.vertex_id;

しかもこれは入口です。サイクルの扱いや、幅優先か深さ優先かなど、考えることはまだあります。

なお、CypherをもとにしたGQLというISO標準が2024年に公開されました。まだ普及はこれからですが、グラフDBのあいだで書き方がそろっていくことが期待されています。

3.2.4 トリプルストアとSPARQL

トリプルストアは、プロパティグラフとほぼ同じことを、違う言葉で表すモデルです。すべての情報を、3つ組の短い文で持ちます。

書き方の1つがTurtleという形式です。同じ主語についての文は、セミコロンでつなげられます。

@prefix : <urn:example:>.
_:lucy   a :Person;   :name "Lucy";  :bornIn _:idaho.
_:idaho  a :Location; :name "Idaho"; :type "state";
         :within _:usa.
_:usa    a :Location; :name "United States";
         :type "country"; :within _:namerica.
背景

セマンティックWebの遺産

トリプルストアの研究の一部は、2000年代初頭のセマンティックWeb構想から来ています。Webのデータを機械が読める形でも公開しよう、という取り組みでした。構想そのものは成功しませんでしたが、JSON-LD、生物医学のオントロジー、リンクのプレビューに使うOpen Graph、Wikidata、Schema.orgなどに形を変えて生きています。セマンティックWebに興味がなくても、トリプルはアプリの内部データモデルとして良い選択肢になりえます。

RDF：名前がURIになっている理由

Turtleは、RDFというデータモデルを書き表す方法の1つです。RDFはインターネット規模でデータを交換するために作られたので、少し変わったところがあります。主語や述語が、よくURIになるのです。

たとえば述語が、ただの within ではなく <http://my-company.com/namespace#within> になります。理由は、他人のデータと混ぜても名前がぶつからないようにするためです。他の誰かが within に別の意味を持たせていても、URIが違うので衝突しません。このURLが実際に何かのページにつながる必要はなく、ただの名前空間です。

SPARQL

SPARQL（スパークル）は、RDFのトリプルストア用のクエリ言語です。Cypherより先に生まれ、Cypherのパターンマッチングはここから借りています。だからよく似ています。

PREFIX : <urn:example:>

SELECT ?personName WHERE {
  ?person :name ?personName.
  ?person :bornIn  / :within* / :name "United States".
  ?person :livesIn / :within* / :name "Europe".
}
CypherSPARQL
変数person?person
0回以上たどる-[:WITHIN*0..]->:within*
プロパティで絞る(usa {name:'…'})?usa :name "…".

RDFはプロパティと辺を区別しません。どちらも述語です。だから、プロパティの条件も辺の条件も同じ書き方で書けます。

3.2.5 Datalog：小さなルールを積み上げる

Datalogは、SPARQLやCypherよりずっと古く、1980年代の学術研究から生まれました。エンジニアにはあまり知られていませんが、本は「もっと知られるべき」と推しています。Datomic、LogicBlox、CozoDB、LinkedInのLIquidなどが採用しています。

土台はグラフではなくリレーショナルモデルです。それでもここで扱うのは、グラフの再帰的なクエリが特に得意だからです。

データはファクトと呼びます。1つのファクトは、テーブルの1行です。

location(1, "North America", "continent").
location(2, "United States", "country").
location(3, "Idaho", "state").

within(2, 1).    /* アメリカは北アメリカの中 */
within(3, 2).    /* アイダホはアメリカの中 */

person(100, "Lucy").
born_in(100, 3). /* Lucyはアイダホ生まれ */

クエリは、いきなり答えを取りに行きません。ルールを1つずつ定義して、新しい仮想のテーブルを作っていきます。SQLのビューに近いものです。

/* ルール1：どの場所も、自分自身の「中」にある */
within_recursive(LocID, PlaceName) :-
  location(LocID, PlaceName, _).

/* ルール2：中の中も、中（自分を呼ぶ＝再帰） */
within_recursive(LocID, PlaceName) :-
  within(LocID, ViaID),
  within_recursive(ViaID, PlaceName).

/* ルール3：どこで生まれ、どこに住んでいるか */
migrated(PName, BornIn, LivingIn) :-
  person(PersonID, PName),
  born_in(PersonID, BornID),
  within_recursive(BornID, BornIn),
  lives_in(PersonID, LivingID),
  within_recursive(LivingID, LivingIn).

/* ルール4：アメリカ → ヨーロッパだけ取り出す */
us_to_europe(Person) :-
  migrated(Person, "United States", "Europe").

読み方は、:- の左が「作るテーブル」、右が「条件」です。右側のパターンが全部マッチしたら、左側の行ができたものとして扱われます。

Datalogは、他の言語とは違う頭の使い方をします。コードを小さな関数に分けて、互いに呼び出すのに似ています。関数が再帰できるように、ルールも自分自身を呼べます。それがグラフをたどる力になります。

3.2.6 GraphQL：わざと不自由にしてある言語

GraphQLは、ここまでの言語と性格が違います。設計上、できることをかなり絞ってあります。

目的は1つです。スマホアプリやWebフロントエンドが、「この画面を描くのに必要な形のJSON」をサーバーに頼めるようにすることです。

クエリ：チャットアプリの画面に必要なもの

query ChatApp {
  channels {
    name
    recentMessages(latest: 50) {
      timestamp
      content
      sender  { fullName imageUrl }
      replyTo { content sender { fullName } }
    }
  }
}

レスポンス：クエリと同じ形のJSON

{ "data": { "channels": [ {
  "name": "#general",
  "recentMessages": [
    { "timestamp": 1693143014,
      "content": "Hey! How are y'all doing?",
      "sender": {"fullName": "Aaliyah", "imageUrl": "https://..."},
      "replyTo": null },
    { "timestamp": 1693143024,
      "content": "Great! And you?",
      "sender": {"fullName": "Caleb", "imageUrl": "https://..."},
      "replyTo": {
        "content": "Hey! How are y'all doing?",
        "sender": {"fullName": "Aaliyah"} } }
  ] } ] } }
うれしいところ
  • 返ってくるのは、頼んだ項目だけ。多くも少なくもない
  • 画面に項目を足したいとき、クライアントのクエリを直すだけ。サーバーのAPIは変えなくていい
コスト
  • クエリを内部サービス（RESTやgRPC）への呼び出しに変換する仕組みが要る
  • 認可、レート制限、パフォーマンスが悩みになる

制限が強い理由は、クエリが信頼できない相手（ユーザーの端末）から来るからです。重いクエリを大量に投げられたら、サーバーが落ちます。

  • 再帰クエリは禁止。Cypher、SPARQL、SQL、Datalogと違うところです。
  • 自由な検索条件も禁止。「アメリカ生まれでヨーロッパ在住の人」のような検索は、サービス側がわざわざ用意しない限りできません。
  • 結合も宣言されたものだけ。GraphQLのスキーマに明示された結合しか頼めません。

上のレスポンスには重複があります。同じ人が何度も発言すれば、名前と画像URLは毎回くり返されます。返信先のメッセージも、IDではなく中身ごと複製されています。

これはわざとです。レスポンスは大きくなりますが、画面を描くコードが単純になります。IDだけ返すと、そのメッセージが直近50件に入っていないとき、クライアントはもう1回サーバーに聞きに行くことになります。

サーバーの中のDBは、正規化して持っていてかまいません。クエリを受けたときに結合して、この形に組み立てます。

最後に名前の話です。「graph」と付いていますが、GraphQLはグラフDB専用ではありません。リレーショナルでもドキュメントでも、どんなDBの上にも作れます。

5つの言語を並べる

言語相手再帰ひとこと
Cypherプロパティグラフできる矢印の絵で書く
SQLリレーショナルできるが長いWITH RECURSIVE
SPARQLトリプルストアできるCypherの先輩
Datalogリレーショナル得意ルールを積む
GraphQL何でも禁止画面用のJSONを頼む
3.3

イベントソーシングとCQRS

ひとことで言うと

「いまの状態」を上書きせず、「起きたこと」を追記し続ける。読むための形は、そこから何個でも作る。

ここまでのモデルは全部、書いた形のまま読むものでした。JSONで書いたらJSONで読む。行で書いたら行で読む。

でも複雑なアプリでは、あらゆる読み方を満たす「たった1つの形」が見つからないことがあります。それなら、書く形と読む形を分けてしまえばいい。これがこの節のアイデアです。

では、読みやすさを一切気にせず、書くことだけに最適化するとどうなるか。答えはイベントログです。何か起きるたびに、時刻つきの自己完結したデータ（たとえばJSON）を、列のうしろに足すだけです。

ログの中のイベントはイミュータブルです。変更も削除もしません。新しいイベントを足すだけです。あとのイベントが前のイベントの効果を打ち消すことはあります。

例：カンファレンス管理システム

本の例はカンファレンスの申し込みです。意外と複雑な業務です。個人がカードで申し込む。企業がまとめて席を買い、請求書で払い、あとから誰が座るか決める。スピーカーやスポンサー用の席を取り置く。キャンセルが出る。会場が変わって定員が変わる。こうなると、「空席はいくつ？」を出すだけで難しいクエリになります。

コマンド
ユーザーからのリクエスト。「予約したい」。まだ事実ではないので、検証して断ることができます。
イベント
検証を通って事実になったもの。過去形で名づけます。「席が予約された」。あとでキャンセルしても、一度予約したという事実は消えません。キャンセルは別のイベントとして足します。
マテリアライズドビュー＝プロジェクション ＝リードモデル
イベントログから作った、読むための形。
イベントソーシング
イベントを情報源にして、状態の変化をすべてイベントで表す考え方。
CQRSコマンドクエリ責務分離
書く用の表現と読む用の表現を分け、読む用を書く用から導くという原則。

大事なルールがあります。ログに入るのは有効なイベントだけです。だから、ログを読んでビューを作る側は、イベントを拒否できません。断れるのは、コマンドの段階までです。

スタースキーマのファクトテーブルとは何が違う？

ファクトテーブルイベントログ
同じ点どちらも、過去に起きた出来事の集まり
行の形全行が同じカラムイベントの種類ごとに、中身が違う
順序順序なし順序が命。予約の前にキャンセルは処理できない

うれしいところ

  1. 「なぜ」が伝わる。「予約がキャンセルされた」のほうが、「bookingsの行4001のactiveがfalseになり、seat_assignmentsから3行消え、paymentsに返金の行が入った」よりずっとわかりやすいです。
  2. ビューは作り直せる。ビューを消して、同じイベントを同じ順に同じコードで流せば、同じものができます。ビューを作るコードにバグがあったら、直して作り直すだけです。
  3. 用途ごとにビューを持てる。クエリごとに最適な形を、いくつでも作れます。読みやすいように非正規化してかまいません。再起動のたびに作り直してよいなら、メモリ上にだけ置くこともできます。
  4. あとから育てやすい。新しい見せ方が欲しくなったら、既存のログから新しいビューを作ります。新しい種類のイベントも足せます。「キャンセルが出たら、順番待ちの次の人に席を回す」のような動きも、あとから連鎖させられます。
  5. 間違いを取り消せる。誤ったイベントは、取り消しのイベントを足して打ち消します。下流のビューは自動で直ります。直接更新するDBでは、コミット済みの変更を戻すのは大変です。
  6. 監査ログになる。何が起きたかが全部残ります。規制の厳しい業界で役立ちます。
  7. 書き込みが速い。うしろに足すだけなので、普通のDBより高いスループットをさばけます。急にイベントが増えてもログが受け止め、ビュー側は自分のペースで追いつけます。

困るところ

  1. 外部の情報に頼ると、作り直しで結果が変わる。たとえば通貨換算です。処理するときに為替レートを取りに行くと、別の日に作り直したとき違う金額になります。対策は、レートをイベントの中に入れておくか、「その時刻のレート」をいつでも同じ値で引けるようにすることです。つまり処理を決定的にします。
  2. 個人データを消せない。イベントは変更しないのが原則ですが、GDPRなどでユーザーは削除を要求できます。ログがユーザーごとに分かれていれば丸ごと消せますが、混ざっていると難しい。個人データをイベントの外に置く、あとで捨てられる鍵で暗号化する（暗号シュレッディング）、といった手があります。ただしその分、作り直しは難しくなります。
  3. 再処理で副作用がまた起きる。ビューを作り直すたびに、確認メールがもう一度飛んでは困ります。

イベントソーシングは、どんなDBの上にも作れます。専用のものとしてはEventStoreDB、MartenDB（PostgreSQLベース）、Axon Frameworkがあります。Kafkaのようなメッセージブローカーにログを置き、ストリームプロセッサでビューを更新する構成もあります（12章）。

ただ1つの必須条件

すべてのビューが、ログに並んでいるのとまったく同じ順序でイベントを処理すること。イベントを保存するシステムは、これを保証しなければなりません。分散システムでは、これが意外と難しい。その話は10章です。

3.4

データフレーム、行列、配列

ひとことで言うと

表のデータを、機械学習が食べられる「数字の行列」に変えていくための道具。

ここまでのモデルは、トランザクション処理にも分析にも使われます。この節のモデルは違います。分析や科学の世界のもので、OLTPにはほとんど出てきません。

データフレームは、R言語、Pythonのpandas、Apache Spark、ArcticDB、Daskなどが持っているモデルです。機械学習の訓練データを用意するデータサイエンティストに人気があります。

見た目は、DBのテーブルやスプレッドシートに似ています。できることも似ています。

  • 全部の行に関数を当てる
  • 条件で行を絞る
  • カラムでグループ化して集約する
  • キーで別のデータフレームとくっつける（DBの結合。データフレームではマージと呼びます）

違うのは使い方です。SQLのように「欲しい結果」を宣言するのではなく、コマンドを順番に当てて、少しずつ形を変えていきます。問いに答えられる形になるまで、データをこねていく感じです。作業はたいてい、手元のマシンにコピーしたデータの上でやります。

表を行列に変える

データフレームのよくある使い道は、リレーショナル風の表を、行列に変えることです。多くの機械学習アルゴリズムは、行列の形の入力を求めるからです。

映画が数千本あれば、列も数千になります。こんな表はRDBにはうまく収まりません。データフレームや、NumPyのような疎配列を扱えるライブラリなら大丈夫です。

数字でないものを、数字にする

行列に入れられるのは数字だけです。数字でないデータは、数字に直します。

  • 日付は、適当な範囲の浮動小数点数にスケーリングします。
  • 決まった選択肢から選ぶ値（映画のジャンルなど）は、ワンホットエンコーディングにします。選択肢ごとに列を作り、当てはまる列に1、それ以外に0を入れます。

全部が数字の行列になれば、線形代数の計算ができます。線形代数は多くの機械学習アルゴリズムの土台です。さっきの評価の行列は、「この人が好きそうな映画」をすすめるレコメンドの材料になります。

仲間たち

  • 配列データベース。TileDBのように、大きな多次元の数値配列の保存に特化したDBです。地理空間の計測データ、医療画像、天文台の観測データなど、科学の分野でよく使われます。
  • 時系列データ。金融業界では、資産価格や取引の移り変わりをデータフレームで表します。
  • バッチ処理。人気があるので、SparkやFlinkにもデータフレームが入っています（11章）。
3.5

まとめと理解度チェック

モデルデータの形向いている場面
リレーショナルテーブルと行結合、多対一、多対多。分析ではスタースキーマとSQLが定番
ドキュメント自己完結したJSON一対多の木。ドキュメント同士の関係がまれなとき
グラフ頂点と辺何でも何にでもつながる。何ホップもたどるクエリ
イベントソーシング追記専用のイベントログ複雑な業務の記録。読む形はCQRSでビューにする
データフレーム多数のカラムを持つ表、行列機械学習、統計、科学計算への橋渡し

章全体から持ち帰ることは3つです。

  • モデル同士は真似し合える。でも真似は不格好。グラフをRDBに入れることはできます。ただ、SQLの再帰クエリで見たとおり扱いにくい。だから各モデルに専用のDBがあります。
  • 一方で、DBは隣の領域に広がっている。RDBはJSONカラムを持ち、ドキュメントDBは結合を持ち、SQLのグラフ対応も少しずつ良くなっています。
  • スキーマは、あるかないかではない。リレーショナル以外のモデルは、たいていスキーマを強制しません。変化に強くなる反面、アプリは結局なにかの形を前提にしています。違いは、スキーマが明示的（書くときに強制）か、暗黙的（読むときに仮定）かだけです。
本が触れなかったモデル

ゲノムデータ。とても長い文字列（DNA）を、似ているが同じではない大量の文字列と照らし合わせます。ここで見たどのDBも向かないので、GenBankのような専用ソフトがあります。

台帳。金融システムの多くは複式簿記の台帳をモデルにします。RDBでも表せますが、TigerBeetleのような専用DBもあります。暗号通貨やブロックチェーンも分散台帳が土台です。

全文検索。DBと並べてよく使う、一種のデータモデルです。検索インデックスとベクトル検索は4章で少し出てきます。

理解度チェック

答えを頭の中で言ってから、開いてください。

正規化と非正規化。書き込みが速いのは？ 読み取りが速いのは？

書き込みが速いのは正規化（コピーが1つだけ）。読み取りが速いのは非正規化（結合が少ない）。良し悪しではなくトレードオフです。

Xのタイムラインのキャッシュが、本文を持たずIDだけ持つのはなぜ？

いいね数やアイコンは頻繁に変わるので、複製してもすぐ古くなり、容量も食うから。読むときにIDから引く（ハイドレーション）ほうが理にかなっています。

ドキュメントモデルが向くのは、データがどんな形のとき？

一対多の関係でできた木の形で、たいてい木を丸ごと読むとき。多対多が多い、入れ子の中身を直接指したい、という場合はリレーショナルが向きます。

「スキーマレス」が誤解を招くと言われるのはなぜ？

読むコードは何らかの構造を前提にしていて、暗黙のスキーマは存在するから。DBが強制していないだけです。正確にはスキーマオンリードと呼びます。

グラフのクエリを普通のSQLで書くと長くなるのはなぜ？

辺を1本たどるのが結合1回にあたり、何本たどるかが事前に決まらないから。WITH RECURSIVE で再帰を書く必要があります。

コマンドとイベントの違いは？

コマンドはリクエストで、検証して断れる。イベントは検証を通った事実で、過去形で名づけ、あとから変更も拒否もできません。

イベントソーシングで、ビューを作り直すときに気をつけることを1つ。

為替レートのような外部情報に頼ると結果が変わること。メール送信のような副作用がまた起きること。どちらかが言えれば正解です。
