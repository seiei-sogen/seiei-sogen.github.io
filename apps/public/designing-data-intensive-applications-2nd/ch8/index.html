トランザクション

ひとことで言うと、「いくつかの読み書きを1つの塊にして、全部成功か、全部なかったことにする」仕組みの話です。

  • 8.1トランザクションって何？ACID の本当の意味
  • 8.2弱い分離レベル同時実行で起きる5つの事故
  • 8.3シリアライザブル事故ゼロにする3つの作り方
  • 8.4分散トランザクション2相コミットとその弱点
  • 8.5まとめ全体を1枚の表で

まず、なぜ要るのか

データを扱うシステムでは、いろんなことが壊れます。

  • DB のソフトやハードが、書き込みの途中で落ちる
  • アプリが、一連の処理の途中でクラッシュする
  • ネットワークが突然切れる
  • 複数のクライアントが同時に書いて、お互いを上書きする
  • 半分しか更新されていない、意味不明なデータを読んでしまう

これを全部アプリ側で面倒を見るのは地獄です。そこでトランザクション。「途中」や「同時」の面倒を DB に押しつけて、アプリのコードを単純にするための道具です。

ポイント

トランザクションは自然法則ではありません。プログラミングを楽にするために人間が作った発明です。だから「どこまで保証してくれるか」は製品ごとに違います。この章はその「どこまで」を見ていきます。

歴史を30秒で

1975年の IBM System R が元祖。2000年代後半の NoSQL ブームで「スケールしないから」と捨てられました。でも CockroachDB、TiDB、Spanner、FoundationDB、YugabyteDB などの「NewSQL」が、分散していてもトランザクションはできると示しました。

8.1トランザクションって正確には何？

8.1.1ACID の意味

トランザクションの保証は「ACID」の4文字で語られます。ただし本は辛口で、「ACID 準拠」はほぼマーケティング用語になっていると言います。DB ごとに中身が違うからです。

A

原子性Atomicity

途中で失敗したら、それまでの書き込みを全部捨てる。本当は「アボート可能性」と呼ぶほうが正確。

C

一貫性Consistency

「貸方と借方は必ず釣り合う」のようなデータのお約束（不変条件）が守られている。

I

分離性Isolation

同時に走っている他のトランザクションに邪魔されない。

D

永続性Durability

「コミット成功」と言われたデータは、クラッシュしても消えない。

A：原子性は「同時実行」の話ではない

マルチスレッドの「アトミック」は「途中の状態が他スレッドから見えない」という意味です。でも ACID の A は違います。「途中でコケたらどうなるか」の話です。同時実行の話は I（分離性）の担当です。

C：一貫性は、実は DB の性質ではない

「お約束」を知っているのはアプリです。DB にできるのは、外部キー制約やユニーク制約など宣言された制約を守らせることだけ。宣言していないお約束を破るデータを書いても、DB は止められません。本はこう言います。ACID の C は、アプリが DB をどう使うか次第であり、DB 単体の性質ではない、と。

「一貫性」という言葉の罠

同じ単語に少なくとも5つの意味があります。レプリカの一貫性、一貫性のあるスナップショット、コンシステントハッシング、CAP 定理の一貫性（＝線形化可能性）、そして ACID の一貫性。全部別物です。

I：分離性がないとこうなる

教科書的な分離性はシリアライザブルです。「同時に走らせても、1個ずつ順番に実行したのと同じ結果になる」という意味です。でもこれは遅いので、現実の DB の多くはもっと弱い保証で動いています。Oracle には「serializable」という名前のレベルがありますが、中身はもっと弱いスナップショット分離です。

D：永続性に「完璧」はない

1台の DB なら、ログ先行書き込み（WAL）と fsync でディスクに確実に書くこと。レプリケーションしているなら、何台かにコピーが届くこと。どちらにも穴があります。

ディスクだけ

マシンが壊れたら、直すまで読めない。SSD は電源断で約束を破ることがある。データが静かに腐ることもある。

レプリケーションだけ

停電や同じバグで全ノードが同時に落ちたら、メモリ上のデータは消える。非同期だとリーダー障害で直近の書き込みが消える。

だから本の結論は「ディスク書き込み、レプリケーション、バックアップを組み合わせろ」です。絶対の保証はどこにもありません。

8.1.21個のオブジェクト vs 複数のオブジェクト

A と I は「1つのトランザクションで複数書き込んだとき」の約束です。メールの例で、今度は分離性のほうを見ます。

「どの読み書きが同じトランザクションか」は、RDB では普通 BEGIN から COMMIT までです（クライアントとの TCP 接続の上で区切ります）。多くの非リレーショナル DB には、この「まとめる」手段がありません。

1個のオブジェクトなら、だいたい守ってくれる

20kB の JSON を書いている途中で回線が切れたら？ 電源が落ちたら？ 途中を誰かに読まれたら？ これは困りすぎるので、ほぼすべてのストレージエンジンが1オブジェクト単位の原子性と分離性は用意しています。アトミックなインクリメントや、条件付き書き込み（CAS）もその仲間です。

でもそれは普通の意味の「トランザクション」ではありません。次の場面では複数オブジェクトをまとめる必要があります。

  • 外部キー：参照する行と参照される行を、ずれないように書く
  • 非正規化したデータ：同じ情報を持つ複数のドキュメントを一緒に更新する
  • セカンダリインデックス：行本体とインデックスを一緒に更新する

エラーとリトライの落とし穴

ACID な DB の哲学は「約束を破りそうなら、中途半端に残さず全部捨てる」です（リーダーレスレプリケーションの DB は逆で、ベストエフォート。失敗しても巻き戻さないので、後始末はアプリの仕事です）。捨ててくれるならリトライすればいい。ただし、リトライにも罠があります。

リトライ5つの罠
  1. 本当は成功していて、返事だけ届かなかった → リトライで二重実行
  2. 原因が過負荷なら、リトライは火に油 → 回数制限と指数バックオフ
  3. 意味があるのは一時的なエラーだけ（デッドロック、瞬断、フェイルオーバー）。制約違反は何回やっても同じ
  4. メール送信など DB の外の副作用は巻き戻らない
  5. リトライ中にクライアント自体が死ねば、書こうとしたデータは消える

8.2弱い分離レベル

同時実行のバグは、タイミングが悪いときだけ起きます。だからテストで見つからず、再現もできません。そして理屈で考えるのも難しい。

DB は「分離」でこれを隠そうとしますが、完全な分離（シリアライザブル）は遅い。そこで「一部の事故だけ防ぐ」弱いレベルが広く使われています。これは理論上の話ではなく、ビットコイン取引所の破綻のような実害が出ています。攻撃者がわざと同時リクエストを大量に投げて、競合状態を突いてくることもあります。

8.2.1リードコミッテッド

いちばん基本のレベルです。約束は2つだけ。

ダーティリードなし

読むときは、コミット済みのデータしか見えない。

ダーティライトなし

書くときは、コミット済みのデータしか上書きしない。

未コミットの値が読めると何が困るか。①複数行の更新の半分だけ見えてしまう。②あとでロールバックされる、結局存在しなかった値を見てしまう。

どう実装しているか

  • ダーティライト対策：行ロック。書きたい行のロックを取り、コミットかアボートまで持ち続ける。
  • ダーティリード対策：書き込み中の行について、古いコミット済みの値と新しい値の両方を持っておく。他の人には古いほうを見せる。

読むときにもロックを取る方法はあまり使われません。長い書き込みが1つあるだけで、読むだけの人が全員待たされるからです。

リードコミッテッドで防げないもの

最初のカウンターの例（42 → 43）は防げません。B の書き込みは A のコミット後なので、ダーティライトではないからです。これは後で出てくる「ロストアップデート」です。

8.2.2スナップショット分離とリピータブルリード

リードコミッテッドでも起きる事故を見ます。

画面を再読み込みすれば直るので、この例は軽傷です。でも次の2つは致命的です。

  • バックアップ：何時間もかかる。一部が古く一部が新しいバックアップから復元したら、不整合が永久に残る。
  • 分析クエリ・整合性チェック：違う時点が混ざったデータを集計しても意味がない。
スナップショット分離とは

各トランザクションは、自分が始まった瞬間の DB の「写真」を最後まで見続けます。あとから他人が何をコミットしても、写真は変わりません。

仕組み：MVCC（マルチバージョン並行性制御）

写真を実現する方法は単純です。行を上書きせず、バージョンを全部取っておく。各トランザクションには増え続ける番号（txid）を振り、各バージョンに「誰が作ったか」「誰が消したか」を書いておきます。更新は内部的に「削除＋挿入」です。

見える・見えないのルールはこうです。次の3つは無視し、それ以外は見えます。

  1. 自分が始まったとき、まだ進行中だったトランザクションの書き込み（その後コミットしても無視）
  2. 自分より後に始まったトランザクションの書き込み
  3. アボートしたトランザクションの書き込み
スナップショット分離の合言葉

読む人は書く人を待たせない。書く人は読む人を待たせない。読み取りにロックが要らないので、長い集計と普通の書き込みが同居できます。

名前がぐちゃぐちゃ

SQL 標準は1975年の System R が元で、スナップショット分離という概念がありません。そのせいで呼び名が DB ごとに違います。

  • PostgreSQL の「リピータブルリード」＝ スナップショット分離
  • Oracle の「シリアライザブル」＝ スナップショット分離
  • MySQL の「リピータブルリード」＝ スナップショット分離より弱い
  • IBM Db2 の「リピータブルリード」＝ シリアライザブル

名前を信じず、その DB が実際に何を防ぐかを確認しましょう。

8.2.3ロストアップデートを防ぐ

ここからは「書く人 vs 書く人」の事故です。いちばん有名なのがロストアップデート。「読む → 手元で変える → 書き戻す」を2人が同時にやると、片方の変更が消えます。最初のカウンターの図がまさにこれです。

  • カウンターの加算、口座残高の更新
  • JSON の中のリストに要素を足す
  • Wiki ページを2人が同時に編集して、ページ全体を保存する

対策は5つあります。

① アトミックな書き込み

読んでから書くのをやめて、DB に計算させる。使えるならこれが最善。

② 明示的なロック

FOR UPDATE で、読んだ行を先に押さえる。

③ 自動検出

並行に走らせて、DB が検出したらアボート。アプリはリトライ。

④ 条件付き書き込み

「読んだときから変わっていなければ」更新する（CAS）。

⑤ マージ

レプリケーション環境では、両方の値を残して後で合体させる。

-- ① アトミックな書き込み：DB の中で足し算する
UPDATE counters SET value = value + 1
WHERE key = 'foo';

-- ② 明示的なロック：読んだ行を押さえてから考える
BEGIN;
SELECT * FROM figures
 WHERE name = 'robot' AND game_id = 222
 FOR UPDATE;
-- アプリ側で「この手は有効か」を判定してから
UPDATE figures SET position = 'c4' WHERE id = 1234;
COMMIT;

-- ④ 条件付き書き込み：中身が昔のままなら更新
UPDATE wiki_pages SET content = '新しい内容'
 WHERE id = 1234 AND content = '読んだときの内容';
-- 更新件数が 0 なら、読み直してリトライ
それぞれの注意点
  • ① ORM を使うと、うっかり「読んで・変えて・書く」コードを書きやすい。
  • ② ロックを1か所付け忘れるだけで事故る。複数ロックするとデッドロックの危険。
  • ③ PostgreSQL のリピータブルリード、Oracle のシリアライザブル、SQL Server のスナップショット分離は自動検出する。MySQL/InnoDB のリピータブルリードは検出しない。
  • ④ DB の実装によっては安全でないことがある。条件判定が古いスナップショットを見るなら、すり抜ける。
  • ⑤ マルチリーダーやリーダーレスでは、「最新のコピーは1つ」という前提が崩れるので、ロックも CAS も効かない。加算のように順番を入れ替えても結果が同じ操作ならきれいにマージできる。LWW（最後の書き込みが勝つ）はロストアップデートを起こしやすい。

8.2.4ライトスキューとファントム

もっとわかりにくい事故があります。病院の当直（オンコール）管理アプリで考えます。ルールは「最低1人はオンコールでなければならない」。

これはダーティライトでもロストアップデートでもありません。2人が更新したのは別々の行だからです。同じものを読んで、別のものを書く。それでも結果がおかしくなる。これがライトスキューです。

ライトスキューの型（全部これ）
  1. SELECT で条件を確認する（2人以上いるか、予約が空いているか）
  2. 結果を見て、アプリが「やっていい」と判断する
  3. 書き込む。その書き込みが、1 の答えを変えてしまう

同じ型の例です。

  • 会議室予約：空きを確認して予約を INSERT。2人同時だと二重予約。
  • マルチプレイヤーゲーム：別々の駒を同じマスに動かす。
  • ユーザー名の取得：未使用を確認して登録。これはユニーク制約で簡単に解決できる。
  • 二重支払いの防止：残高を確認して使う。2件同時だと残高がマイナスに。

なぜ防ぎにくいか

  • 複数の行が絡むので、1オブジェクトのアトミック操作は役に立たない。
  • ロストアップデートの自動検出も効かない（PostgreSQL、MySQL、Oracle、SQL Server のどれも、スナップショット分離相当のレベルでは検出しない）。
  • 「最低1人」のような複数行にまたがる制約は、ほとんどの DB に組み込みがない。
  • 本当の解決はシリアライザブル。使えないなら次善の策は、判断の根拠にした行を FOR UPDATE でロックすること。

ファントム：ロックする行がそもそも無い

当直の例では、手順1で読んだ行をロックできました。でも会議室予約は違います。手順1で確認したのは「該当する行が存在しないこと」です。存在しない行に FOR UPDATE は掛けられません。

あるトランザクションの書き込みが、別のトランザクションの検索結果を変えてしまう。この現象をファントム（幽霊）と呼びます。

最後の手段：コンフリクトの実体化

ロックする相手がいないなら作ってしまう方法です。「部屋 × 15分の時間枠」の行をあらかじめ全部作っておき、予約時にその行をロックします。ただし、並行性制御の都合がデータモデルに漏れ出すので醜い。本は、できる限りシリアライザブルのほうがいいと言います。

8.3シリアライザブル

ここまでの話をまとめると、弱い分離レベルはつらい。

  • レベルの意味が難しく、DB ごとに実装が違う。
  • アプリのコードを見ても、そのレベルで安全かどうかわからない。
  • 競合状態を見つけてくれる良い道具がない。

研究者の答えは1970年代からずっと同じです。「シリアライザブルを使え」。

シリアライザブルとは

トランザクションを同時に走らせても、結果は「1個ずつ順番に実行した場合」のどれかと同じになる、という保証。つまり、起こりうる競合状態を全部防ぎます。

じゃあなぜ皆使わないのか。作り方が3つあり、それぞれに代償があるからです。

8.3.1作り方① 本当に1個ずつ実行する

同時実行の問題をなくすいちばん単純な方法は、同時実行をやめることです。1本のスレッドで、順番に1個ずつ。

当たり前に見えますが、現実的になったのは2000年代です。理由は2つ。

  • RAM が安くなった。データを全部メモリに置けば、ディスク待ちがなくて速い。
  • OLTP のトランザクションは短いと気づいた。長い分析クエリは読み取り専用なので、スナップショットで別に走らせればいい。

ストアドプロシージャが必須になる

普通のトランザクションは、アプリと DB が何往復も会話します。その往復の待ち時間のあいだ、1本しかないスレッドが止まったら全員が待たされます。だから、処理をまるごと DB に送って一気に実行させます。

ストアドプロシージャは評判が悪いです。DB ごとの独自言語（PL/SQL など）、デバッグ・テスト・デプロイのしにくさ、下手なコードが DB 全体を遅くする危険。でも今どきの実装は汎用言語を使います（VoltDB は Java や Groovy、Datomic は Java や Clojure、Redis は Lua）。

1コアの壁とシャーディング

1本のスレッドなので、書き込み性能はCPU 1コア分が上限です。データをシャードに分け、各シャードに1スレッドを割り当てれば伸ばせます。ただし複数シャードにまたがるトランザクションは調整が必要で、桁違いに遅くなります（VoltDB で毎秒約1,000件）。

逐次実行が使える条件
  • すべてのトランザクションが小さくて速いこと。遅いのが1つあると全部止まる。
  • よく使うデータがメモリに収まること。
  • 書き込み量が1コアで足りるか、シャードをまたがずに分割できること。

8.3.2作り方② 2相ロック（2PL）

約30年間、シリアライザブルの実装といえばこれだけでした。考え方は「危なそうなら待たせる」。

2PL ≠ 2PC

名前が似ていますが完全に別物です。2PL（2相ロック）は分離性のため。2PC（2相コミット、8.4）は分散環境の原子性のため。

ロックには2種類あります。読むときは共有ロック、書くときは排他ロック。

「2相」の意味は、①実行中にロックを取っていく相と、②コミットかアボートのときに全部手放す相。途中では手放しません。

欠点：遅い、そして不安定

  • 待ち行列ができる。遅いトランザクション1つで、システム全体が詰まることがある。
  • 応答時間が読めない。高パーセンタイルがとても遅くなる。
  • デッドロックが頻発する。DB が検出して片方をアボートし、アプリがやり直す。その分の仕事は無駄になる。

ファントムはどう防ぐ？ 述語ロックとインデックス範囲ロック

会議室予約のように「まだ無い行」を守るには、行ではなく検索条件そのものにロックを掛けます。これが述語ロック。「部屋123の正午から13時に重なる予約」という条件をロックすれば、これから挿入される行にも効きます。

ただし、条件どうしの突き合わせは重い。そこで実際の DB はインデックス範囲ロック（ネクストキーロック）で近似します。「部屋123の全予約」や「その時間帯の全部屋」のように、広めに雑にロックする。余計な人も待たせますが、判定が軽い。使えるインデックスが無ければ、テーブル全体をロックします。

8.3.3作り方③ シリアライザブルスナップショット分離（SSI）

性能が悪いか（2PL）、スケールしないか（逐次実行）、事故が起きるか（弱いレベル）。この三択しかないのか。SSI はそこへの答えです。スナップショット分離に近い軽さで、完全なシリアライザブルを実現します。

悲観的（2PL）

「事故るかも」と思ったら先に待たせる。逐次実行は、その究極形。

楽観的（SSI）

とりあえず全員走らせる。コミットのときに検査して、まずかった人だけアボート。

楽観的な方法は、ぶつかり合いが多いとアボートだらけになって遅くなります。でも余力があってぶつかり合いが少なければ、悲観的な方法より速い。

SSI が見張っているもの

ライトスキューの正体は「古くなった前提で判断した」ことでした（「オンコールは2人いる」）。そこで SSI は、スナップショット分離の上に「前提が古くなっていないか」の検出を足します。見張るのは2つの場合です。

3つの作り方を並べる

① 逐次実行② 2PL③ SSI
考え方並行をやめる悲観的：待たせる楽観的：後で検査
待ち全員が順番待ち読み書きが互いに待つ待たない
失敗の形遅い Tx が全体を止めるデッドロックコミット時のアボート
弱点1コアの壁遅くて不安定長い読み書き Tx はアボートされやすい
例VoltDB、Redis、DatomicMySQL と SQL Server のシリアライザブルPostgreSQL のシリアライザブル、CockroachDB、FoundationDB

SSI のコツは、読み書きするトランザクションを短くすること。長い読み取り専用のものは問題ありません。

8.4分散トランザクション

ここからは、1つのトランザクションが複数のノードにまたがる場合です（複数シャードへの書き込みなど）。分離性の作り方は1台のときと大差ありません。まったく新しい難題は原子性です。

1台なら簡単でした。データを書き、最後に「コミットした」という記録をディスクに書く。その記録が書けた瞬間がコミットです。決めるのは1台だけ。

複数台だと、全員に「コミットして」と送るだけでは足りません。

8.4.12相コミット（2PC）

解決策の古典です。コーディネーターという司会役を置き、コミットを2段階に分けます。

結婚式のたとえ

司式者が2人それぞれに「結婚しますか？」と聞く。両方が「誓います」と答えたら、「結婚が成立しました」と宣言する。どちらかが「はい」と言わなければ中止。

なぜ2段階だとうまくいくのか：約束の仕組み

2PC には引き返せない地点が2つあります。

地点1：参加者の「はい」

「はい」と答えたら、アボートする権利を手放す。クラッシュしても停電しても必ずコミットできるよう、データをディスクに書いてから答える。

地点2：司会の記録

コーディネーターが決定をディスクに書いたら、もう覆せない。届かなければ、届くまで永遠に送り直す。

結婚式でいえば、「誓います」と言ってしまった後は、直後に気絶しても結婚は成立している、ということです。

弱点：司会が倒れると全員が固まる

助かる道は、コーディネーターが復活してログを読み直すことだけです。そのログが消えていたら、人間の管理者が手作業で決めるしかありません。

3相コミット（3PC）は？

固まらない方式として提案されましたが、「ネットワーク遅延にも応答時間にも上限がある」という前提が必要です。現実のネットワークにそんな上限はないので、原子性を保証できません。実用的な答えは、コーディネーターを合意プロトコルで多重化すること（第10章）。

8.4.2異なるシステムをまたぐ場合

「分散トランザクション」には、まったく違う2種類があります。

DB 内部の分散 Tx

全ノードが同じソフト。CockroachDB や Spanner など。自由に最適化できる。

ヘテロな分散 Tx

別々の製品をまたぐ。別ベンダーの DB どうし、DB とメッセージブローカーなど。ずっと難しい。

何がうれしいか：「厳密に1回」の処理

メッセージキューからメッセージを受け取り、DB に書く処理を考えます。「メッセージの受領確認」と「DB の書き込み」を1つのトランザクションにできれば、途中で落ちても両方なかったことになり、安全に再配信できます。結果として、何度リトライしても効果は1回分だけ。

ただし、関わる全システムが同じアトミックコミットの手順に対応している必要があります。メール送信サーバーが対応していなければ、リトライのたびにメールが飛びます。

XA：異種システム用の 2PC 規格

1991年に登場した標準規格です。ネットワークプロトコルではなく、コーディネーターとやり取りするための C 言語の API（Java なら JTA）。多くの場合、コーディネーターはアプリと同じプロセスの中のライブラリで、ログはアプリサーバーのローカルディスクに書かれます。

XA のつらいところ
  • ロックを握ったまま固まる。未確定のあいだ、参加者は行ロックを手放せない。コーディネーターが20分落ちれば、ロックも20分そのまま。ログが消えていれば永遠に。関係ない他のトランザクションまで巻き添えで止まる。
  • 孤児トランザクション。ログの破損やバグで、結果が永久に決まらないものが残る。DB を再起動しても直らない（ロックを持ち続けるのが正しい実装だから）。管理者が手作業で解決する。
  • 「経験則による決定」という非常口がある。参加者が独断でコミットかアボートを決める機能。本いわく、これは「原子性を壊すかもしれない」の婉曲表現。
  • コーディネーターが単一障害点。しかもアプリサーバーの中にいるので、アプリサーバーが「消えては困るログを持つ機械」になってしまう。
  • 最小公倍数の機能しか使えない。どんな製品とも話せる必要があるので、システムをまたいだデッドロック検出はできず、SSI とも組み合わせられない。

8.4.3DB 内部の分散トランザクション

NewSQL 系（CockroachDB、TiDB、Spanner、FoundationDB、YugabyteDB）や Kafka は、内部で分散トランザクションを使います。多くは 2PC ですが、XA の問題を抱えていません。他の製品に合わせる必要がないからです。直し方はこうです。

  1. コーディネーターを多重化する。落ちたら別のノードが自動で引き継ぐ。
  2. コーディネーターとシャードが直接話す。あいだにアプリのコードを挟まない。
  3. 参加するシャードも多重化する。1台の故障でアボートになる危険を減らす。
  4. アトミックコミットと並行性制御を連携させる。シャードをまたいだデッドロック検出と、一貫した読み取りができる。

多重化には合意アルゴリズムを使います（第10章）。分離レベルは製品によりますが、スナップショット分離も SSI もシャードをまたいで実現できます。

8.4.4「厳密に1回」をもう一度考える

実は「厳密に1回」のために、分散トランザクションは必須ではありません。DB の中のトランザクションだけで作れます。

ここで出てくる大事な言葉：冪等（べきとう）

ID を記録することで、同じメッセージを何回処理しても結果が1回分と同じになります。これが冪等。Kafka Streams などのストリーム処理も同じ考え方です（第12章）。

8.5まとめ

トランザクションは抽象化の層です。いろんな種類の失敗を「アボート」という1種類にまとめてくれる。アプリはリトライするだけでよくなります。

どのレベルが、どの事故を防ぐか

事故の名前を一行ずつ

ダーティリード他人のコミット前の書き込みを読む
ダーティライト他人のコミット前の書き込みを上書きする
リードスキューDB の別々の部分を別々の時点で見る
ロストアップデート「読む・変える・書く」が重なり、片方の変更が消える
ライトスキュー読んで判断して書いたが、書く頃には判断の前提が崩れている
ファントムリード他人の書き込みが、自分の検索結果を変える

この章を5行で

持ち帰り
  1. トランザクションは「全部か、ゼロか」。失敗をアボート1種類にまとめる道具。
  2. 「ACID」という看板ではなく、実際にどの分離レベルかを見る。名前は DB ごとに意味が違う。
  3. 弱いレベルは一部の事故しか防がない。残りはアプリがロックなどで手当てする。
  4. 全部防げるのはシリアライザブルだけ。作り方は逐次実行・2PL・SSIの3つ。
  5. 複数ノードの原子性は 2PC。司会が倒れると固まるのが弱点で、DB 内部なら司会の多重化で直せる。
