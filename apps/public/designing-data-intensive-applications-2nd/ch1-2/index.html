1.2 クラウドとセルフホスティング

ひとことで言うと、「自分で面倒を見るか、お金を払って人に任せるか」の話です。どちらが正しいという結論はなく、何と引き換えに何を得るかを整理する節です。

オレンジ＝自分でやる 青＝人に任せる
30秒でわかる 1.2
  1. ソフトには「誰が作るか」と「誰が動かすか」の2つの選択がある。
  2. クラウドは楽で伸び縮みできる。そのかわり自分でコントロールできない。
  3. クラウド前提で設計されたシステム（クラウドネイティブ）は、計算する場所とデータを置く場所を分ける。
  4. クラウドにしても運用の仕事はなくならない。中身が変わるだけ。

＝ クラウドサービス／SaaS

判断のものさし

自社ならではの強みになるものは自分でやる。どこの会社でも同じ、ありふれたものは買ってくる。

極端な例：CPUを自分で作る会社はほぼありません。半導体メーカーから買うほうがずっと安いからです。

選択肢は白黒ではなく、グラデーション

本の図1-2にあたる図です。上に行くほど自分でやることが多く、下に行くほど任せることが多くなります。

自分でやる任せる

自作して、自分で動かす

作る：自分動かす：自分

例：自社専用に書いたシステム

ここがセルフホスト（既製品を自分でデプロイ）

既製ソフトを自社のマシンで動かす

作る：他人動かす：自分マシン：自前

例：MySQLをダウンロードして自社サーバーに入れる。オンプレミスと呼ぶ。

既製ソフトを借りたVMで動かす

作る：他人動かす：自分マシン：借り物

例：MySQLをクラウドの仮想マシンに入れる。マシンだけ借りる形を IaaS と呼ぶ。

クラウドサービス／SaaS

作る：他人動かす：他人

WebやAPI越しに使うだけ。中身には触れない。

言葉のメモ
  • オンプレミス：自社で管理するハードで動かすこと。サーバーが借りたデータセンターのラックに置いてあっても、こう呼ぶのがふつう。
  • IaaS（Infrastructure as a Service）：クラウドのVMを借りること。中で何を動かすかは自由、そのかわり面倒も自分で見る。
  • Kubernetesなど「どうやってデプロイするか」の道具選びは、データシステムの設計への影響が小さいので、この本では扱わない。
1.2.1

クラウドサービスの良いところ、悪いところ

クラウド会社は「うちを使えば安くて速い」と言います。でも本当にそうかは自分たちのスキルと負荷の波しだいです。

運用のやり方をもう知っている。
負荷もだいたい読める。
→
自前のほうが安いことが多いマシンを買って自分で動かす
そのシステムの動かし方をまだ知らない。
→
クラウドのほうが早くて楽専任の人を雇って育てるのはとても高い
負荷が時間によって大きく上下する。
→
クラウドが特に得意使う分だけ借りて、終わったら返せる

なぜ「負荷の波」が大事なのか

自前のマシンは、いちばん混む瞬間に耐えられる台数を買っておく必要があります。すると、ひまな時間はずっとマシンが遊んでいます。

自前：ピークに合わせて買う
クラウド：負荷に合わせて増やして、減らす

図はイメージです。山のときだけ借りて、終わったらクラウド会社に返します。

波が激しい代表：分析システム

大きな分析クエリは、大量のマシンを並列に使って一気に終わらせたい。でも終わった瞬間、次のクエリまでマシンはひまになります。データが巨大で、速く結果がほしいほど、クラウドで「使い終わったら返す」効果が大きくなります。データが小さければ差は小さめです。

日次レポートのような決まったクエリは、順番待ちにして波をならせます。人がその場で投げるクエリではそれが難しい。

サービスの質はどっちが上？

任せた場合

相手は運用のプロ。たくさんの顧客を相手にする中でノウハウがたまっていく。自分でやるより質が高いかもしれない。

自分で動かす場合

自社の使い方にぴったり合うように設定やチューニングができる。クラウド側がそこまでやってくれることはまずない。

なお、クラウドにしても運用チームは必要です（1.2.3で出てきます）。基本的な管理を任せることで、もっと上のレイヤーの課題に集中できる、という話です。

最大の欠点：自分でコントロールできない

お店のカレーは、厨房に入って直すことができません。クラウドも同じです。

ほしい機能がない

お願いするしかない。自分で実装することはふつうできない。

サービスが落ちた

復旧を待つしかない。

遅い、バグっぽい

原因を調べにくい。自前ならOSのメトリクスやサーバーログを見られるが、クラウドでは中が見えない。

終了・値上げ・仕様変更

相手の都合に振り回される。古いバージョンを使い続ける手はたいてい使えず、引っ越すことになる。標準のAPIがないと引っ越し代が高い。これがベンダーロックイン。

国と国がもめた

締め出されるおそれ。提供元が外国の会社だと、制裁で使えなくなるリスクがある。

データを預けている

相手を信じるしかない。プライバシーやセキュリティの規制に対応する手続きがややこしくなる。

それでも現実は

これだけリスクがあっても、クラウドの上に新しいアプリを作る会社は増え続けています。一部だけクラウドにするハイブリッドも一般的です。

ただし全部がクラウドに移るわけではありません。クラウド以前からある古いシステムは残りますし、特殊な要件のものは自前が必要です。たとえば高頻度取引は遅延に極端に敏感なので、ハードウェアを完全に自分で握りたい。

1.2.2

クラウドネイティブなシステムアーキテクチャ

クラウドが変えたのは「買う」から「月額で借りる」というお金の払い方だけではありません。データシステムの作り方そのものも変えました。

クラウドに引っ越しただけ

もともと自分で動かす前提のソフトを、クラウド会社が代わりに動かして提供する（マネージドサービス）。

クラウドネイティブ

最初からクラウドの強みを活かす前提で設計したシステム。

最初からクラウド用に作ると何がうれしいか
  • 同じハードウェアでも性能が出る
  • 障害からの復旧が速い
  • 負荷に合わせてすばやく増減できる
  • もっと大きなデータを扱える

1.2.2.1

クラウドサービスは「積み木」になっている

セルフホスト型のソフトが必要とするものは素朴です。OS、ファイルシステム、ネットワーク。つまり普通のコンピュータがあれば動きます。クラウドのVMも、すぐ用意できてサイズが選べること以外は普通のコンピュータと同じです。

クラウドネイティブは発想が違います。OSの上に直接乗るのではなく、下位のクラウドサービスの上に、上位のサービスを積むのです。

セルフホスト型

▲
1台のマシン（またはVM）CPU・メモリ・ディスク・ネットワーク

Snowflakeの上に作られたサービス
▲ 乗っている

オブジェクトストレージ（S3、Azure Blob Storage、Cloudflare R2 など）とは

大きなファイルを置く場所です。できることは普通のファイルシステムより少なく、基本は「ファイルを書く・読む」だけ。そのかわり裏のマシンを意識しなくていい。

  • データは自動で多数のマシンに分散される。ディスク容量切れを心配しなくていい。
  • マシンやディスクが丸ごと壊れても、データは消えない。
積み木のどの段を使うか

上の段ほど、特定の用途に特化しています。自分のやりたいことに合うなら、上の段を使うほうがずっと楽。合うものがなければ、下の段の部品から自分で組み立てるしかありません。唯一の正解はありません。

1.2.2.2

ストレージとコンピュートの分離

この節でいちばん大事な図です。「計算する係（CPU・メモリ）」と「データを覚えておく係（ディスク）」を、別々のものにします。

従来：1台が両方を担当
CPU・メモリ計算する係
ディスク覚えておく係
ディスク（コピー）RAIDで二重化

「ディスクに書いたものは消えない」が前提。ディスク1本の故障には、同じマシンに複数のディスクをつないでコピーを持つ RAID で備える。

クラウドネイティブ：係を分ける
コンピュートCPU・メモリ
コンピュートCPU・メモリ
＋ 増やす／減らす
↑↓ ネットワーク越しに読み書き ↑↓
ストレージサービスデータを長く保存する場所。多数のマシンに分散

計算する側だけを増やしたり減らしたりできる。データは別の場所にあるので、計算マシンが消えても困らない。

なぜ分けるのか。クラウドのVMについているローカルディスクは、当てにできないからです。VMが壊れたり、負荷に合わせて大きい（小さい）VMに取り替えられたりすると、別の物理マシンに移るので、元のローカルディスクにはもう届きません。

では、クラウドでデータをどこに置くか。3つの置き場所があります。

VMのローカルディスク

いつ消えてもおかしくない。→ 長期保存には使わず、一時的なキャッシュとして扱う。

仮想ディスク（Amazon EBS など）

あるVMから外して別のVMにつなぎ直せるディスク。正体は本物のディスクではなく、別のマシン群が「ディスクのふり」をしているサービス（ブロックデバイス。1ブロックはふつう4 KiB）。

良い点：ディスク前提の昔ながらのソフトがそのまま動く。
悪い点：ふりをする分のオーバーヘッドがある。読み書きが毎回ネットワーク通信になるので、ネットワークの調子に振り回されやすい。

用途に合わせた専用ストレージサービス

クラウドネイティブはふつうこちら。仮想ディスクを避け、ワークロード向けに最適化されたストレージサービスを土台にする。

S3のようなオブジェクトストレージは、数百KB〜数GBくらいの大きめのファイル向き。データベースの1行はずっと小さいので、クラウドDBでは小さな値は別のサービスで管理し、たくさんの値をまとめた大きなブロックをオブジェクトストアに置くのが一般的（くわしくは4章）。

分けたことの代償

S3はファイルを置いておくだけです。そのデータを分析したければ、S3の外で計算する必要があり、データをネットワーク越しに運ぶことになります。この話は次の1.3（分散システム）につながります。

マルチテナント：一戸建てではなくマンション

クラウドネイティブなシステムの多くは、顧客ごとに専用マシンを用意しません。複数の顧客のデータと計算を、同じハードウェア・同じサービスで処理します。

1.2.3

クラウド時代の運用

「クラウドにすれば運用はいらない」は間違いです。この項の結論は仕事の中身が変わるだけで、必要性は変わらないです。

運用する人の呼び名の変化

DBA（データベース管理者）、システム管理者
サーバー側のデータ基盤を専門に管理する人たち。
DevOps
開発と運用の役割をまとめ、バックエンドのサービスとデータ基盤の両方に1つのチームで責任を持つ考え方。
SRE（Site Reliability Engineer）
その考え方をGoogleが形にしたもの。
運用の仕事は大きく2つ
  • ユーザーに確実に届ける：インフラの設定、アプリのデプロイ
  • 本番を安定させる：信頼性をおびやかす問題の監視と診断

相手にするものが「マシン」から「サービス」へ

セルフホストの運用

マシン1台ずつの世話が多い。

  • ディスクの空きを見張り、足りなくなる前に足す
  • 新しいマシンを用意する
  • サービスを別のマシンへ移す
  • OSにパッチを当てる

クラウドサービスを使う運用

マシンはAPIの向こうに隠れている。

  • 固定サイズのディスクではなく従量課金。先に容量を決めなくても保存でき、使った分だけ払う
  • マシンが1台壊れても、サービスは動き続けることが多い
DevOps／SREが大事にすること
  • 手作業の一発仕事より、自動化して繰り返せる手順にする
  • 長生きするサーバーより、使い捨てのVMやサービスを使う
  • アプリをこまめに更新できるようにする
  • 障害から学ぶ
  • 人が入れ替わっても、システムの知識が組織に残るようにする

運用は2種類に分かれた

クラウド会社の運用チーム

大勢の顧客に、止まらないサービスを届けるための細かい技術を極める。

  • 自分のアプリと、使っているライブラリのセキュリティ

  • サービスにかかる負荷の監視
  • 遅くなった、落ちた、というときの原因追跡
1.2.3 の結論

クラウドは運用の役割を変えつつある。でも運用が必要なことは、これまでと何も変わらない。

理解度チェック

質問をタップすると答えが開きます。

Q1. MySQLをクラウドのVMにインストールして使う。これはセルフホスト？ クラウドサービス？

セルフホストです。マシンは借り物（IaaS）ですが、既製のソフトを自分でデプロイして自分で面倒を見ています。

Q2. 負荷がほぼ一定で、運用のノウハウも社内にある。安くなりやすいのはどっち？

自前でマシンを買って動かすほうが安いことが多いです。クラウドの「使い終わったら返す」強みが活きないからです。

Q3. クラウドネイティブなシステムが、VMのローカルディスクを長期保存に使わないのはなぜ？

VMが壊れたり、別のサイズのVMに取り替えられたりすると、そのローカルディスクにはもう届かなくなるからです。だから一時的なキャッシュとして扱い、データは別のストレージサービスに置きます。

Q4. 仮想ディスク（EBSなど）の弱点は？

ディスクのふりをするオーバーヘッドがあること。そして読み書きがすべてネットワーク通信になるので、ネットワークの不安定さの影響を受けやすいことです。

Q5. 従量課金になると、キャパシティプランニングは何に変わる？

財務計画に変わります。同じように、パフォーマンス最適化はコスト最適化になります。
