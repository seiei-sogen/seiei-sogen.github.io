シャーディング

データが1台のマシンに入りきらなくなったら、切り分けて何台かに配ります。この章は「どう切り分けるか」と「配ったあとに何が面倒になるか」の話です。

  • 1行目シャーディングは、データを分割して別々のマシンに置くこと。目的は「書き込み」と「データ量」をさばくこと。
  • 2行目分け方は大きく2つ。キーの範囲で分けるか、キーのハッシュで分けるか。
  • 3行目分けたあとの面倒ごとは3つ。リバランシング、ルーティング、セカンダリインデックス。

7.0

そもそもシャーディングとは

データを複数のマシン（ノード）に置く方法は2つあります。6章でやったレプリケーションと、この章のシャーディングです。

ルールは1つだけ。どのレコードも、必ずどれか1つのシャードに入る。シャード1個は「小さなデータベース」だと思って大丈夫です。

ふつうは両方いっしょに使う

シャードに分けたうえで、各シャードをさらに何台かにコピーします。分けるのは容量のため、コピーするのは壊れても平気にするためです。

分け方（シャーディング）とコピーの仕方（レプリケーション）は、ほぼ別々に選べます。なのでこの章では、コピーのことはいったん忘れて「分け方」だけを考えます。

呼び名がバラバラ問題

同じものなのに、製品ごとに名前が違います。ドキュメントを読むときに混乱しがちなので、対応表を置いておきます。

製品シャードの呼び名

CockroachDBレンジ
HBase、TiDBリージョン
CouchbasevBucket
Riakvnode
Cassandraトークンレンジ
Bigtable、YugabyteDB、ScyllaDBタブレット
まぎらわしい言葉 2つ

PostgreSQL のパーティショニングは、大きなテーブルを同じマシンの中で複数ファイルに分ける機能です。複数マシンに分けるほうをシャーディングと呼んで区別します。ほかの多くのシステムでは、この2語は同じ意味です。

ネットワーク分断（network partition）は、ノード間の通信が切れる障害のこと。データを分ける話とは無関係です（9章で登場）。

7.1

シャーディングの長所と短所

やる理由は1つ、スケーラビリティです。マシンを大きくする代わりに、台数を増やして容量を増やせます（水平スケーリング、スケールアウト）。

ただし効くのはデータ量と書き込みが1台の限界を超えたときです。読み込みが多いだけなら、6章のリードレプリカを増やせば足ります。

著者のおすすめ

1台でさばける間は、シャーディングしない。最近のマシンは1台でもかなり強いです。シャーディングは大規模向けの「重い」解決策で、入れた瞬間にシステムが複雑になります。

何が複雑になるのか

  • パーティションキー選び

    どのレコードをどのシャードに入れるかを決めるキーです。同じキーのレコードは同じシャードに入ります。居場所がわかれば速い。わからなければ全シャードを探すはめになります。あとから変えるのも大変です。

  • インデックスと結合

    キーバリュー型は分けやすい。リレーショナルは、セカンダリインデックスでの検索や、別シャードにあるレコードどうしの結合が難しくなります（7.5で詳しく）。

  • 分散トランザクション

    1回の書き込みが複数シャードにまたがると、全体のつじつまを合わせる仕組みが必要です。単一ノードのトランザクションよりずっと遅く、ボトルネックになることもあります（8章）。

豆知識：1台の中でもシャーディング

Redis、VoltDB、FoundationDB は、CPUコアごとに1プロセスを動かし、コアの間でデータを分けています。1台のマシンの並列性を使い切るためのシャーディングです。

7.2

マルチテナンシーのためのシャーディング

SaaSでは、契約している会社（テナント）ごとにデータが独立しています。A社の顧客リストとB社の顧客リストが混ざることはありません。それなら、テナントごとにシャードを分けてしまおう、という使い方です。

うれしいこと7つ

  • リソース分離

    ある会社が重い処理を走らせても、別シャードの会社は巻き添えを食いにくい。

  • パーミッション分離

    アクセス制御にバグがあっても、置き場所が物理的に別なら他社のデータが見えてしまう事故は起きにくい。

  • セルベースアーキテクチャ

    DBだけでなくアプリのサーバーも含めて、テナント群ごとに「セル」という箱にまとめる。障害がそのセルの中で止まります。

  • テナント単位のバックアップ

    ある会社がデータを消してしまっても、その会社のシャードだけを巻き戻せます。

  • 規制対応

    GDPRやCCPAの「自分のデータを出して」「消して」という要求に、そのシャードのエクスポートと削除で応えられます。

  • データレジデンシー

    「このテナントのデータはこの国に置く」という決まりを、シャードの置き場所で満たせます。

  • 段階的なスキーマ変更

    マイグレーションを1テナントずつ進められる。全員に広がる前に問題に気づけます。

つらいこと3つ

  • 巨大テナント

    1社が1台に収まらないほど大きいと、その会社の中でまたシャーディングが必要。ふりだしに戻ります。

  • 小さいテナントが大量

    1社1シャードは無駄が大きい。まとめて同居させると、育った会社をどう引っ越すかという問題が出ます。

  • テナントをまたぐ機能

    複数の会社のデータを組み合わせる機能は、シャードをまたぐ結合になり、作るのが難しい。

7.3

どのレコードをどこに置くか

ここが章の本丸です。目標は、データと負荷を全ノードに均等に配ること。均等に配れれば、10台で1台の10倍をさばけます。

用語意味
スキューシャードごとのデータ量や負荷が偏っていること
ホットシャード負荷が集中しているシャード（ホットスポットとも）
ホットキー負荷が集中している1つのキー（例：有名人のアカウント）
リバランシングノードを足したり引いたりしたとき、均等になるよう配り直すこと

必要なのは、パーティションキーを渡すとシャードを返す関数です。しかも、あとで配り直しやすい関数でなければなりません。候補を順に見ていきます。

7.3.1　キーの範囲で分ける

紙の百科事典と同じやり方です。「この巻はここからここまで」と、キーの連続した範囲をシャードに割り当てます。

  • 得意なこと

    シャードの中はキー順に並んでいます。だから「11月の計測値を全部」のような範囲スキャンが速い。

  • 苦手なこと

    近いキーに書き込みが集中すると、そのシャードだけが忙しくなります。

典型的な事故：タイムスタンプをキーにする

センサーの計測値を、時刻をキーにして保存するとします。シャードは「9月分」「10月分」「11月分」のようになります。今の時刻の書き込みは、すべて今月のシャードに行きます。

範囲方式のリバランシング：大きくなったら割る

シャードが育ちすぎたら2つに割り、片方を別のノードに移します。データが減ったら、隣どうしをくっつけます。Bツリーのページ分割と同じ発想です。

  • いいところ

    シャードの数がデータ量についてきます。少ないうちは少数、増えたら自動で増える。

  • つらいところ

    分割は重い作業です。しかも割りたいシャードは、たいてい今いちばん忙しい。追い打ちになります。

  • 事前分割

    空のDBに最初からシャードを切っておく機能（HBase、MongoDB）。キーの分布を前もって知っている必要があります。

使っている製品：境界を手で決める Vitess。自動で決める Bigtable、HBase、MongoDB（範囲オプション）、CockroachDB、RethinkDB、FoundationDB。YugabyteDB は両対応。

7.3.2　キーのハッシュで分ける

「近いキーを近くに置きたい」という事情がないなら、キーをハッシュ関数に通してバラバラにしてしまうのが定番です。ハッシュ関数は、似た入力からでも似ても似つかない数を出します。同じ入力なら必ず同じ数です。

言語に組み込みのハッシュは使えない

Java の Object.hashCode() や Ruby の Object#hash は、同じキーでもプロセスが違うと別の値になることがあります。シャーディングには不向きです。MongoDB は MD5、Cassandra と ScyllaDB は Murmur3 を使っています。暗号として強い必要はありません。

問題はここからです。出てきたハッシュ値を、どうやってシャードに結びつけるか。4つの方法を、ダメなものから順に見ます。

方法① ノード数で割った余り（ダメな例）

最初に思いつくのはこれでしょう。

const node = hash(key) % nodeCount;

計算は簡単です。でもnodeCountが変わった瞬間、ほとんどのキーの答えが変わります。下のボタンでノードを増やしてみてください。

方法② シャードの数を最初に固定する

単純なのに広く使われている方法です。ノード数よりずっと多いシャードを最初に作ってしまい、1つのノードにたくさん持たせます。たとえば10ノードに1,000シャード（1台あたり100個）。キーの行き先は hash(key) % 1000 で決め、この「1000」は二度と変えません。

  • いいところ

    シャードを丸ごと運ぶだけなので、分割より安い。性能の高いノードに多めに持たせる、という調整もできます。

  • 弱点1：上限がある

    シャード数より多いノードは持てません。足りなくなったら、全シャードを割り直す重い作業（リシャーディング）が待っています。止めないとできないシステムもあります。

  • 弱点2：ちょうどいい数がわからない

    シャード数が固定だと、データが増えるほど1シャードが太ります。太すぎると引っ越しと復旧が重い。細かすぎると管理の無駄が増える。将来のデータ量が読めないと決めにくい。

使っている製品：Citus（PostgreSQLのシャーディング層）、Riak、Elasticsearch、Couchbase。

引っ越しには時間がかかります。運んでいる最中の読み書きは、古い割り当てのまま処理されます。

方法③ ハッシュ値の範囲で分ける

シャード数を前もって読めないなら、範囲方式の「大きくなったら割る」を借りてきます。ただし範囲を切る対象は、キーそのものではなくハッシュ値です。

  • いいところ

    負荷が散らばる。そのうえ、シャード数をデータ量に合わせて後から増やせます。

  • 失うもの

    パーティションキーでの範囲クエリです。「10:00〜10:05のキー」は全シャードに散らばっているので、全部に聞くしかありません。

範囲クエリを取り戻す技：複合キー

キーを (user_id, timestamp) の2列にして、ハッシュにかけるのは先頭の user_id だけにします。同じユーザーのレコードは全部同じシャードに入り、その中では時刻順に並びます。「このユーザーの先週分」は1シャードの範囲スキャンで済みます。

使っている製品：YugabyteDB、DynamoDB。MongoDB でもオプションで選べる。

方法③の変形：Cassandra と ScyllaDB

ハッシュ値の空間をランダムな位置で区切り、1つのノードに複数の範囲を持たせます。範囲の大きさはバラバラですが、何個も持てば平均されます。

データウェアハウスにも同じ考え方がある

BigQuery は「パーティションキー」でパーティションを決め、「クラスタカラム」でその中の並び順を決めます。Snowflake は「マイクロパーティション」と「クラスタキー」。Delta Lake にもパーティションとクラスタキーがあります。呼び名が違うだけで、複合キーの技と同じ構造です。

方法④ コンシステントハッシング

特定のアルゴリズムの名前というより、次の2つを満たす方式の総称です。

  • 各シャードに入るキーの数が、だいたい同じ。
  • シャードの数が変わっても、引っ越すキーができるだけ少ない。

方法①は2つめを満たさないので失格。Cassandra と ScyllaDB の方式は、この考え方の元祖に近いものです。ほかにランデブーハッシングやジャンプコンシステントハッシングがあります。こちらは範囲を切り取るのではなく、全ノードから少しずつ個々のキーを集めて新入りに渡します。

ここでの「コンシステント」は別の意味

レプリカの一貫性（6章）とも、ACIDのC（8章）とも関係ありません。「キーがなるべく同じ場所に居続ける」という意味です。

7.3.3　それでも残るホットスポット

ハッシュが均等にしてくれるのはキーの数です。負荷ではありません。フォロワーが何百万人もいる有名人が投稿すると、その1つのキーに読み書きが殺到します。キーが1つである以上、ハッシュではばらせません。

  • 対策A：専用シャードを与える

    範囲で区切る方式なら、ホットキー1つだけのシャードを作れます。専用のマシンを割り当てることもできます。

  • 対策B：アプリ側でキーを割る

    ホットキーの末尾にランダムな数字を付けて、別々のキーとして書き込みます。

対策Bの代償
  • 読むときは100個のキーを全部読んで、合体させる必要がある。
  • 散るのは書き込みだけ。読み込みの負荷は減らない。
  • 全キーにやると無駄なので、ホットなキーだけにしたい。すると「どのキーを割ったか」の管理が要る。

さらに厄介なのは、負荷が時間で変わることです。バズった投稿は数日で静かになります。書き込みで熱いキーと読み込みで熱いキーでは、打つ手も違います。大規模なクラウドサービスはここを自動化していて、Amazon はヒートマネジメントやアダプティブキャパシティと呼んでいます。

7.3.4　リバランシングは自動か、手動か

  • 全自動

    運用が楽です。負荷に合わせて増減するオートスケールもできます。DynamoDB は、負荷の大きな増減に数分で追いつけるとうたっています。

  • 人間が承認

    遅いけれど、予想外の事故を防げます。大型セールやチケット発売のように、混む日がわかっているなら先回りして配り直せます。

  • その中間

    Couchbase と Riak は、配り直しの案をシステムが作ります。管理者が承認するまで実行されません。

全自動が怖いのは、「落ちたノードを自動で検知する仕組み」と組み合わさったときです。

7.4

リクエストルーティング

配り方が決まったら、次の疑問はこれです。「このキーを読みたい。どのIPアドレスの、どのポートにつなげばいい？」

アプリのサーバーなら、どのインスタンスも同じ仕事ができるので、ロードバランサーが適当に振り分ければ済みます。データベースは違います。そのキーを持っているノードしか答えられません。

やり方は3通りあります。

どの方式でも出てくる3つの難問

  • 誰が配置を決める？

    決める係（コーディネーター）は1つがいちばん単純。でもそれが落ちたら？ 交代のときに決める係が2人になったら（スプリットブレイン）？

  • 変更をどう知る？

    シャードが別のノードに移ったことを、住所録を持つ側はどうやって知るのか。

  • 引っ越し中は？

    新しいノードが引き継ぐ途中で、古いノードに向かって飛んでいるリクエストをどうするか。

よくある答え：住所録の管理を専門家に任せる

多くのシステムは、ZooKeeper や etcd のようなコーディネーションサービスに住所録を預けます。これらは合意アルゴリズム（10章）を使っていて、一部が落ちても動き続け、スプリットブレインも防ぎます。

住所録の管理方法使っている製品
ZooKeeperHBase、SolrCloud
etcdKubernetes（どのサービスがどこで動いているかの管理）
自前の専用サーバーMongoDB（コンフィグサーバー＋ルーティング層の mongos）
組み込みの RaftKafka、YugabyteDB、TiDB、ScyllaDB
ゴシッププロトコルRiak

Riak だけ毛色が違います。ノードどうしがうわさ話のように状態を伝え合う方式で、合意プロトコルより保証が弱く、ノードによって住所録が食い違うこともあります。リーダーレスのデータベースはもともと一貫性の保証が弱いので、それを受け入れられます。

補足2つ

最初につなぐ先（ルーティング層や適当なノード）のIPアドレスは、めったに変わらないので DNS で十分なことが多いです。

ここまでの話は「1つのキーを読み書きする」OLTP向けです。分析系のクエリは、たくさんのシャードを並列に読んで集計します。そちらは11章で。

7.5

シャーディングとセカンダリインデックス

ここまでの方式には、隠れた前提がありました。読みたいレコードのパーティションキーを知っていることです。

でも実際のアプリは「赤い車を全部」「この単語を含む記事を全部」のように、キー以外でも検索します。そのためのセカンダリインデックスは、シャードときれいに対応しません。赤い車はどのシャードにもいるからです。

中古車サイトを例にします。出品IDがパーティションキーで、ID 0〜499 がシャード0、500〜999 がシャード1。色（color）とメーカー（make）で絞り込みたいとします。

7.5.1　ローカルインデックス：各シャードが自分のぶんだけ索引を持つ

  • 書き込みは楽

    車を1台追加するとき、触るのはその車が入るシャード1つだけ。データと索引が同じ場所にあるからです。

  • 読み込みは重い

    全シャードに問い合わせます。並列に聞いても、いちばん遅い1つを待つことになる（末尾遅延の増幅）。シャードを増やしてもクエリの処理能力は上がりません。全クエリが全シャードに行くからです。

例外もあります。パーティションキーがわかっていれば、そのシャードだけに聞けます。全部ではなく何件かあれば足りるなら、どれか1つのシャードで済みます。

使っている製品：MongoDB、Riak、Cassandra、Elasticsearch、SolrCloud、VoltDB。弱点はあっても広く使われている。

7.5.2　グローバルインデックス：全体をカバーする索引を、別の切り口で分ける

全シャードのデータをまとめた索引を作ります。ただし1台に置くとそこが詰まるので、索引もシャーディングします。分ける基準は出品IDではなく、索引の値そのものです。

  • 読み込みが速い

    条件が1つなら、索引シャード1つを読めばIDのリスト（ポスティングリスト）が手に入ります。

  • ただし本体は別

    手に入るのはIDだけ。車の情報そのものが欲しければ、そのIDを持つ各シャードへ取りに行きます。

  • AND検索

    「赤」かつ「Toyota」は、2つのリストが別々の索引シャードにあるのがふつう。両方をネットワーク越しに集めて共通部分を取ります。リストが長いと遅い。

  • 書き込みが難しい

    車を1台追加すると、色の索引とメーカーの索引、別々のシャードを更新することになります。データと索引をずれなく保つには、分散トランザクション（8章）が1つの手です。

使っている製品：CockroachDB、TiDB、YugabyteDB。DynamoDB はローカルとグローバルの両方に対応。

DynamoDB のグローバルインデックスは遅れて反映される

書き込みは非同期で索引に届きます。そのため、索引から読むと少し古いデータが返ることがあります。6章のレプリケーションラグと同じ種類の現象です。

キーバリューストアで索引を自作したくなったら

「値→IDの対応表」をアプリのコードで持てば、索引の代わりになります。ただし、同時書き込みの競合や、片方だけ保存に成功する失敗で、データと索引がずれやすい。細心の注意が要ります（8章のマルチオブジェクトトランザクションの話につながります）。

まとめ

分け方の早見表

  • キー範囲

    範囲クエリが速い。シャード数がデータ量についてくる。近いキーへの書き込みでホットスポット。育ったら分割。

  • hash % ノード数

    使わない。ノード数を変えるとほぼ全キーが引っ越す。

  • 固定数のシャード

    シャード丸ごとの移動で済む。数を最初に決める必要があり、外すと高くつく。

  • ハッシュ範囲

    負荷が散り、シャード数も後から増やせる。パーティションキーでの範囲クエリは非効率。複合キーで補う。

よくある落としどころは、キーの先頭部分でシャードを決め、残りの部分でシャード内を並べる形です。同じパーティションキーの中なら範囲クエリが効きます。

Q1. 読み込みが多すぎて遅い。まずシャーディング？

いいえ。読み込みだけならリードレプリカを増やせば足ります。シャーディングが効くのは、書き込みやデータ量が1台の限界を超えたときです。

Q2. 時刻をキーにしてキー範囲で分けると何が起きる？

書き込みが「今」のシャードに集中してホットシャードになります。キーの先頭にセンサーIDなど別の要素を付けて散らします。

Q3. hash % ノード数 がダメな理由は？

ノード数が変わると、ほとんどのキーの行き先が変わるからです。配り直しのデータ移動が大きすぎます。

Q4. 固定数のシャード方式で、ノードを足したとき変わる対応と変わらない対応は？

変わらないのはキー→シャード。変わるのはシャード→ノードだけです。

Q5. ローカルインデックスで「赤い車を全部」探すと？

全シャードに問い合わせて結果を合体させます。書き込みは1シャードで済む代わりに、検索が重くなります。

Q6. グローバルインデックスのいちばんの弱点は？

1レコードの書き込みが複数の索引シャードに波及することです。データと索引を同期させ続けるのが難しくなります。
