4章 ストレージと検索

データベースの仕事は、つきつめると2つだけです。渡されたデータをしまうこと。頼まれたら取り出すこと。4章は、その裏側でデータベースが何をしているかの話です。

ひとことで

しまい方には大きく3つの流派があります。書き込みに強いログ構造化（LSMツリー）、読み取りに強いBツリー、集計に強い列指向。どれも「何を速くして、何をあきらめるか」が違います。

自分でデータベースを作ることは、たぶんありません。でも、たくさんある中から選ぶことと、設定を調整することはあります。中で何が起きているかを大まかに知っていれば、その判断ができます。それがこの章を読む理由です。

4.1OLTPのためのストレージとインデックス

世界一シンプルなデータベース

本は、たった2つのbash関数で作ったデータベースから始めます。

db_set () {
  echo "$1,$2" >> database
}

db_get () {
  grep "^$1," database \
    | sed -e "s/^$1,//" \
    | tail -n 1
}

db_set は、ファイルの末尾に「キー,値」を1行足すだけです。db_get は、ファイルを全部読んで、そのキーの最後の行を返します。同じキーを何度書いても古い行は消えません。いちばん後ろの行が最新です。

この作りは、良いところと悪いところがはっきりしています。

  • 書き込みはとても速い。末尾に足すだけだからです。これより単純な書き込みはありません。
  • 読み取りは遅い。毎回、先頭から最後まで全部見るからです。データが2倍になれば、時間も2倍かかります。
用語：ログ

この本でいうログは、「末尾に足すことしかしない記録の並び」のことです。アプリが出すエラーログより広い意味で、人間には読めないバイナリのこともあります。この先、何度も出てきます。

インデックスは、読みを速くして書きを遅くする

読み取りを速くするには、探しものの場所を教えてくれる別のデータが要ります。それがインデックスです。データ本体から作る、おまけの構造です。

おまけなので、足しても消してもデータの中身は変わりません。変わるのは速さだけです。ただし、タダではありません。データを書くたびに、インデックスも直す必要があるからです。

この章でいちばん大事なトレードオフ

うまく選んだインデックスは読み取りを速くします。でも、どのインデックスも書き込みを遅くし、ディスクを使います。だからデータベースは、勝手に全部の列へインデックスを張りません。よく使うクエリを知っているあなたが選びます。

4.1.1ログ構造化ストレージ

まずはログ構造化です。ファイルを書き換えず、末尾に足していく方式です。「末尾に足すだけ」の速さを保ったまま、読み取りを速くする工夫を、順番に積み上げていきます。

工夫1：メモリにハッシュマップを持つ

いちばん素朴な方法は、「キー → ファイルの何バイト目にあるか」の対応表をメモリに持つことです。書くたびに表を更新し、読むときは表を見てその場所へ直行します。

全部読むよりずっと速くなります。でも、問題が4つ残ります。

  1. 古い行が消えないので、書き続けるといつかディスクが埋まる。
  2. 表はメモリにしかないので、再起動のたびにファイル全体を読んで作り直す。
  3. キーが多すぎると、表がメモリに入りきらない。
  4. 範囲で探せない。「10000から19999まで全部」と言われても、1個ずつ引くしかない。

工夫2：キーの順に並べる（SSTable）

そこで実際のデータベースは、データをキーの順に並べて持ちます。キー順に並んだファイルをSSTable（Sorted Strings Table）と呼びます。1つのファイルの中に、同じキーは1回しか出てきません。

並んでいると、全部のキーを覚えなくてよくなります。ファイルを数キロバイトのブロックに区切り、各ブロックの最初のキーだけを覚えれば十分です。この、まばらな索引をスパースインデックスと呼びます。

補足（本にはないたとえ）

紙の辞書と同じ仕組みです。辞書の各ページの上には、そのページの最初の単語が書いてあります。全部の単語の場所を覚えていなくても、目当ての単語がどのページにあるかはすぐわかります。

ブロックごとに圧縮もできます。ディスクの節約になり、読み書きするデータ量も減ります。代わりにCPUを少し使います。

工夫3：メモリで受けて、まとめて書き出す

SSTableは読むには良いのですが、書くのが難しくなります。キー順を保つには、途中に割り込ませる必要があるからです。そのたびにファイル全体を書き直すわけにはいきません。

解決策は、追記ログとキー順ファイルのいいとこ取りです。

  1. 書き込みは、まずメモリ上の「キー順を保てる木」に入れる。これをメムテーブルと呼ぶ。
  2. メムテーブルが数メガバイトにたまったら、キー順のままSSTableとしてディスクに書き出す。この1ファイルをセグメントと呼ぶ。書き出している間も、新しいメムテーブルで書き込みを受け続ける。
  3. 読むときは、メムテーブル、新しいセグメント、古いセグメントの順に探す。最後まで無ければ、そのキーは存在しない。
  4. 裏で、セグメント同士をマージして、上書きされた値や消された値を捨てる。これをコンパクションと呼ぶ。
補足（本にはないたとえ）

机の上のトレーと書類棚に似ています。届いた書類はまずトレー（メムテーブル）に入れ、たまったら並べ直して棚（セグメント）にしまいます。棚のファイルは書き換えず、ときどき古いファイル同士をまとめ直します。

マージの動きは、マージソートと同じです。それぞれのファイルを頭から読み、いちばん小さいキーを出力へ写す。これを繰り返します。同じキーが複数のファイルにあれば、新しいほうだけ残します。

細かいけれど大事な点

  • クラッシュ対策。メムテーブルはメモリにあるので、落ちたら消えます。そこで、書き込みのたびにディスク上のログにも追記しておきます。このログはキー順ではありませんが、復元に使うだけなので問題ありません。メムテーブルをSSTableに書き出したら、その分のログは捨てます。
  • 削除。ファイルは書き換えないので、「このキーは消えた」という印を追記します。これを削除マーカー（tombstone）と呼びます。マージのときに、それより古い値が捨てられます。
  • 書き換えないことの利点。マージ中も、古いセグメントで読み取りに答え続けられます。書き出しの途中で落ちても、作りかけのファイルを捨ててやり直すだけです。セグメントをオブジェクトストレージに置くこともできます。
名前の整理

この仕組みをLSMツリー（Log-Structured Merge-tree）と呼びます。RocksDB、Cassandra、ScyllaDB、HBaseがこの方式です。「SSTable」「メムテーブル」という言葉は、GoogleのBigtableの論文から来ています。

ブルームフィルタ：「絶対にない」を一瞬で答える

LSMツリーには弱点があります。存在しないキーや、ずっと前に書いたキーを読むと遅いのです。セグメントをいくつも調べることになるからです。

そこで、セグメントごとにブルームフィルタという小さなビットの列を持たせます。作り方はこうです。キーをハッシュ関数にかけて、いくつかの番号を出す。その番号のビットを1にする。これを全部のキーでやります。

調べたいキーも同じハッシュにかけて、その番号のビットを見ます。

  • 1つでも0があるなら、そのキーは絶対に入っていません。このセグメントは読まずに飛ばせます。
  • 全部1なら、入っている可能性があります。ただし、ほかのキーがたまたまそこを1にしただけかもしれません。これを偽陽性と呼びます。

偽陽性でも害はありません。セグメントを読んでみて「やっぱり無かった」とわかり、少し無駄をするだけです。目安として、キー1個あたり10ビット使うと偽陽性は1%。5ビット足すごとに10分の1になります。

コンパクション戦略：いつ、どれをマージするか

マージのやり方には、代表的な方式が2つあります。

サイズ階層型（size-tiered）は、小さくて新しいSSTableを、大きくて古いSSTableへ順にまとめていきます。

データが書き直される回数が少ないので、書き込みが多い使い方に向きます。ただし古いファイルが巨大になり、マージの間は一時的にディスクをたくさん使います。

レベル型（leveled）は、SSTableの大きさをそろえて、L0、L1、L2…という段に分けます。L0は書きたてのデータです。L1から下は、キーの範囲で担当が分かれています。段がいっぱいになると、一部を下の段へマージします。

少しずつマージするのでディスクの使用量が少なく、調べるファイルも少ないので、読み取りが多い使い方に向きます。ほとんどのLSMツリーは、両方から選べるようになっています。

コラム：組み込みストレージエンジン

データベースには、ネットワーク越しに使うサーバー型のほかに、アプリと同じプロセスの中でライブラリとして動く組み込み型があります。RocksDB、SQLite、LMDB、DuckDB、KùzuDBがその例です。

スマホアプリの中のデータ保存でよく使われます。サーバー側でも、データが1台に収まり、同時に走るトランザクションが多くなければ選択肢になります。たとえば、テナントごとに別々の組み込みデータベースを持たせる設計です。

この章の話は、どちらの型にも当てはまります。

4.1.2Bツリー

次はBツリーです。本ではこちらの方式を同一位置更新（in-place）と呼びます。ディスク上のデータを、その場で上書きする方式です。Bツリーは1970年に登場し、いまでもほぼすべてのリレーショナルデータベースの標準です。MySQLやPostgreSQLで普段使っているインデックスは、これです。

キー順に並べて持つ点はSSTableと同じです。でも、考え方は正反対です。

LSMツリー

データを、大きさの決まっていないセグメント（数MB以上）に分ける。一度書いたら書き換えない。

Bツリー

データを、同じ大きさのページに分ける。ページをその場で上書きする。

ページの大きさは昔から4KiBが普通です。PostgreSQLは8KiB、MySQLは標準で16KiBです。

ページには番号がついていて、ページの中に「別のページの番号」を書けます。ディスク上のポインタです。これでページの木を作ります。

各ページには、キーと、子ページへの参照が交互に並んでいます。キーは「ここが境目」という仕切りです。251を探すなら、200と300の間の参照をたどる。次のページでも同じことをする。そうしてリーフに着きます。

1ページから出ている参照の数を分岐係数と呼びます。図では6ですが、実際は数百です。だから木はとても浅くなります。

数字で見る

分岐係数500、4KiBページ、4階層のBツリーは、最大250TBを収められます。ほとんどのデータベースは3〜4階層で足りるので、探すときに読むページは数枚で済みます。

書き込み：上書きと、ページの分割

値を変えるときは、リーフを探して、そのページを新しい内容で上書きします。キーを足すときは、入るべきページを探して、そこに足します。

ページが満杯だったら、ページを半分ずつ2つに分け、親ページに新しい境目を足します。

この仕組みのおかげで、木はいつもバランスが取れています。キーがn個あっても、深さはO(log n)で済みます。

壊れないための工夫：WAL

上書きには危険があります。ページの分割では、複数のページを書き換えます。その途中でデータベースが落ちると、どの親からも指されないページができるなど、木が壊れます。1ページを書いている途中で落ちて、半分だけ書かれたページが残ることもあります。

そこでBツリーは、先行書き込みログ（WAL、write-ahead log）を持ちます。追記専用のファイルです。

  1. 変更内容を、まずWALに追記する。
  2. fsync でディスクに確実に書き込む。ここまで済めば、データは失われない。
  3. ページの上書きは、そのあとで行う。すぐには書かず、しばらくメモリにためておいてよい。

落ちたあとは、WALを読んで木を正しい状態に戻します。

気づき

その場で上書きするBツリーも、安全のために追記ログを使っています。LSMツリーがメムテーブルを守るのに使ったのも追記ログでした。追記ログは、どちらの流派にも出てくる基本の道具です。

Bツリーの変わり種

  • コピーオンライト。上書きもWALも使わず、変更したページを別の場所に新しく書き、親にはそちらを指す新しい版を作ります。LMDBがこの方式です。
  • キーを縮める。途中のページのキーは境目がわかれば十分なので、短くして詰め込みます。分岐係数が上がり、木が浅くなります。
  • リーフを順番に並べる。範囲スキャンを速くするためですが、木が育つと保つのが難しくなります。
  • リーフ同士をつなぐ。各リーフが左右の隣を指しておくと、親に戻らずに順番に読めます。

4.1.3BツリーとLSMツリーの比較

目安

書き込みが多いならLSMツリー。1件ずつの読み取りが速いのはBツリー。ただしこれは目安です。本は、自分のワークロードで測りなさいと言っています。両方の特徴を混ぜたエンジンもあります。

読み取り

Bツリー

階層ごとに1ページ読むだけ。階層は少ないので速く、かかる時間も予測しやすい。範囲クエリも、並んだ順にたどるだけなので単純で速い。

LSMツリー

コンパクションの進み具合が違うSSTableを、いくつも調べることがある。ブルームフィルタがそれを減らしてくれる。ただし範囲クエリにはブルームフィルタが効かない。全セグメントを並行して読んで結果を合わせるので、1件読むより高くつく。

LSMツリーには、もうひとつ注意点があります。書き込みが激しすぎて、ディスクへの書き出しやコンパクションが追いつかないことがあります。そのときRocksDBなどは、メムテーブルを書き出し終えるまで読み書きをいったん止めます。これをバックプレッシャーと呼びます。応答時間が急に跳ね上がる原因になります。

書き込み：ランダムか、シーケンシャルか

Bツリーは、書くキーがばらばらなら、上書きするページもディスクのあちこちに散らばります。LSMツリーは、セグメントファイルを丸ごと一気に書きます。一般に、まとめて続けて書くほうがスループットは高くなります。だから同じハードウェアなら、LSMツリーのほうが多くの書き込みをさばけます。

この差はHDDで特に大きく、SSDでは小さくなります。それでも無視はできません。

コラム：SSDでもシーケンシャルが有利な理由

HDDでランダムライトが遅いのは、ヘッドを動かして、円盤が回ってくるのを待つからです。SSDにはその動く部品がありません。それでも差が出ます。

フラッシュメモリは、読み書きは1ページ（普通は4KiB）ごとにできますが、消去は1ブロック（普通は512KiB）ごとにしかできません。ブロックの中にまだ要るページが残っていたら、それをよそへ引っ越してからでないと消せません。この引っ越し作業がガベージコレクション（GC）です。

まとめて書いたデータは、ブロックを丸ごと占めやすくなります。あとでそのファイルが消えれば、ブロックをそのまま消去できます。散らばって書くと、要るページと要らないページが混ざり、GCの仕事が増えます。GCが使った書き込みの帯域は、アプリからは使えません。SSDの寿命も縮みます。

書き込み増幅

アプリが1回書いただけでも、ディスクには何度も書き込みが起きます。

用語：書き込み増幅

実際にディスクへ書いたバイト数を、「インデックスなしで追記ログに書くだけなら必要だったバイト数」で割ったものです。これが大きいほど、同じディスクでさばける書き込みは減り、SSDも早く消耗します。

普通のワークロードでは、LSMツリーのほうが書き込み増幅は小さくなりがちです。ページ丸ごとを書かなくてよく、SSTableを圧縮できるからです。

性能を測るときの落とし穴

空っぽのLSMツリーに書いている間は、コンパクションがまだ走っていません。ディスクを全部、新しい書き込みに使えるので速く見えます。データが増えて、コンパクションと帯域を分け合うようになるまで、十分長く測る必要があります。

ディスクの使い方

Bツリー

キーをたくさん消すと、使われないページがファイルの途中に残る。これがフラグメンテーション。あとの追加で再利用はできるが、OSには返しにくい。ページを詰め直す裏方の処理が要る。PostgreSQLのvacuumがその例。

LSMツリー

コンパクションが定期的にファイルを書き直すので、すき間が残りにくい。ブロックの圧縮もよく効き、ファイルは小さくなりやすい。ただし、上書きされた古い値は、コンパクションまで場所を取る。

ほかにも違いが2つあります。

  • 確実に消したいとき。LSMツリーでは、削除マーカーがすべての段に行き渡るまで、消したはずのデータがディスクに残ります。長くかかることもあります。データ保護の規制で「本当に消した」と言う必要があるときは、注意が要ります。
  • スナップショットを取りたいとき。LSMツリーは楽です。メムテーブルを書き出して、その時点のセグメントファイルの一覧を控えるだけ。ファイルは書き換わらないので、消さずに残しておけばコピーも要りません。ページを上書きするBツリーでは、これが難しくなります。

4.1.4セカンダリインデックス

ここまでの話は、キーから値を引く索引でした。リレーショナルデータベースでいえば主キーのインデックスです。

実際には、主キー以外の列でも探したくなります。CREATE INDEX で作るのがセカンダリインデックスです。たとえば user_id 列に張って、同じユーザーの行をまとめて探します。

作り方は主キーの索引とほぼ同じです。違いは、同じ値の行がたくさんあることです。持ち方は2通りあります。

4.1.5インデックスの中に何を入れるか

索引をたどった先に何が置いてあるかは、データベースによって違います。3通りあります。

1. クラスタ化インデックス

MySQLのInnoDBでは、主キーは必ずこれです。SQL Serverでは、テーブルごとに1つ指定できます。

2. ヒープファイル

行を、順番を決めずにヒープファイルという置き場に入れる方式です。PostgreSQLがこれです。

InnoDBのセカンダリインデックスは少し違い、場所の代わりに主キーを持ちます。セカンダリインデックスで主キーを見つけ、それを使って行を引き直します。

3. カバリングインデックス

索引に、キーのほかに一部の列だけを入れておきます。その列だけで答えられるクエリは、行の本体を読まずに済みます。これを「インデックスがクエリをカバーする」と言います。代わりに、データが二重になるのでディスクを使い、書き込みも遅くなります。本の訳語は「カラム格納インデックス」です。

ヒープファイルの弱点

値を更新して、前より大きくなったとします。元の場所に入りきらなければ、行を引っ越すことになります。そのときは、すべての索引を新しい場所に書き換えるか、元の場所に「引っ越し先はこちら」という転送用のポインタを残します。

4.1.6すべてをメモリに保持する

ここまでの構造は、どれも「ディスクは扱いにくい」という制約への答えでした。それでもディスクを使うのは、電源が切れても消えないことと、メモリより安いことが理由です。

メモリが安くなり、データが全部メモリに載るなら、話が変わります。これがインメモリデータベースです。

Memcachedのように、キャッシュ専用で「消えてもいい」と割り切るものもあります。消えたら困る場合は、次のどれかで守ります。

  • 変更のログをディスクに書く。
  • 定期的にスナップショットをディスクに書く。
  • ほかのマシンに複製する。

RedisやCouchbaseは、ディスクへ非同期に書くことで、弱めの永続性を持ちます。

意外な点

インメモリデータベースが速いのは、「ディスクを読まないから」ではありません。ディスク型でも、メモリが十分あればOSがキャッシュするので、ディスクは読まずに済みます。速い理由は、メモリ上のデータ構造をディスクに書ける形へ変換する手間がないことです。

もうひとつの利点は、ディスクでは作りにくいデータ構造を提供できることです。Redisが優先度つきキューや集合を扱えるのは、全部メモリにあって実装が単純になるからです。

4.2分析のためのデータストレージ

ここから話が変わります。OLTPは「少しの行を、速く、大量にさばく」世界でした。分析は「ものすごい数の行を読んで、集計する」世界です。

データウェアハウスもSQLで使うので、外から見るとOLTPのデータベースに似ています。でも中身は別物です。得意なクエリの形がまったく違うからです。1つの製品で両方をこなすデータベース（HTAP）もありますが、それらも内部では、別々の2つのエンジンに分かれつつあります。

4.2.1クラウドデータウェアハウス

BigQuery、Amazon Redshift、Snowflakeのような、クラウド専用のデータウェアハウスが広く使われています。特徴は、計算する層とデータを置く層が分かれていることです。データはオブジェクトストレージに置くので、容量と計算力を別々に増減できます。1.2節で出てきた話です。

オープンソースの世界では、かつてHiveのような1つのシステムにまとまっていた機能が、別々の部品に分かれました。

  • クエリエンジン。SQLを解釈し、実行計画を立てて実行します。Trino、Apache DataFusion、Presto。
  • ストレージフォーマット。表の行を、ファイルの中のバイトとしてどう並べるかを決めます。Parquet、ORC、Lance、Nimble。
  • テーブルフォーマット。ファイルは一度書いたら変えません。そこで「どのファイルの集まりが1つの表か」を管理して、行の追加や削除をできるようにします。Apache Iceberg、Delta Lake。過去の時点の表を読むタイムトラベルもできます。
  • データカタログ。どの表がデータベースにあるかを管理します。SnowflakeのPolaris、DatabricksのUnity Catalog。

4.2.2カラム指向ストレージ

データウェアハウスの中心は、巨大なファクトテーブルです（3章のスタースキーマ）。数兆行、ペタバイトになることもあります。列は100を超えることもよくあります。でも、1つのクエリが使う列は、たいてい4つか5つです。

OLTPのデータベースは行指向です。1行ぶんの値を、隣り合わせに置きます。この置き方だと、3列しか使わないクエリでも、条件に合う行を100列ぶん丸ごとディスクから読んで、要らない部分を捨てることになります。

カラム指向（列指向）の発想は単純です。行ごとではなく、列ごとにまとめて置きます。

行をもとに戻したいときは、各列の同じ番目の値を集めます。23行目が欲しければ、どの列からも23番目を取ります。全部の列が同じ順番で並んでいることが前提です。

実際には、数千〜数百万行ごとのブロックに区切って、その中で列ごとに置きます。ブロックを時間の範囲で分けておけば、「先月ぶん」のようなクエリは、関係するブロックの、使う列だけを読めば済みます。

いまや、ほぼすべての分析用データベースが列指向です。Snowflake、DuckDB、Parquetなどがそうです。

混同注意

ワイドカラム（カラムファミリー）は別物です。Bigtable、HBaseなどのモデルで、名前は似ていますが行指向です。1行の値をまとめて置くからです。

列の圧縮

列ごとに並べると、同じような値が続きます。これは圧縮にとても向いています。代表的な方法がビットマップエンコーディングです。

列に出てくる値の種類は、行数よりずっと少ないのが普通です。売上が何十億件あっても、商品は10万種類かもしれません。そこで、値の種類ごとに「この行はその値か」を0と1で持ちます。

このビットマップは、そのまま検索にも使えます。

  • product_sk IN (31, 68, 69) なら、3本のビットマップをORする。
  • product_sk = 30 AND store_sk = 3 なら、2本のビットマップをANDする。別の列同士でも、k番目のビットは同じ行を指すので成り立つ。

並べる順番

行は届いた順に置いてもかまいません。でも、順番を決めて並べると、それが索引の役目も果たします。

注意点は、列ごとに別々に並べ替えてはいけないことです。どの値が同じ行のものか、わからなくなります。並べ替えは必ず行ごと、全部の列をそろえて行います。

どの列で並べるかは、よく使うクエリから決めます。日付の範囲で絞ることが多いなら、date_key を第1キーにします。同じ日の中は、第2キー（たとえば product_sk）で並べます。

圧縮がいちばん効くのは第1キーの列です。数十億行あっても、数キロバイトに縮むことがあります。第2、第3キーになるほど値は入り混じり、効きは弱くなります。

書き込み

列指向は、並んだ表の途中に1行を割り込ませるのが苦手です。そこから後ろの、圧縮済みの列を全部書き直すことになるからです。データウェアハウスへの書き込みは一括投入が多いので、まとめて書けば問題になりません。

ここでもログ構造化の考え方が使われます。書き込みはまずメモリ上の行指向のストアにため、たまったらディスク上の列ファイルとマージして、新しいファイルとして一気に書き出します。古いファイルは書き換えません。4.1.1と同じ形です。

クエリは、ディスクの列データとメモリの新しいデータの両方を見て、合わせて答えます。使う人にその違いは見えません。Snowflake、Vertica、Apache Pinot、Apache Druidなどがこの方式です。

4.2.3クエリ実行：コンパイルとベクター処理

数百万行を読むクエリでは、ディスクから読む量だけでなく、CPUの時間も問題になります。

いちばん素朴な実行方法は、インタプリタのように、1行ずつ「このクエリは何をしろと言っているか」を確かめながら進むやり方です。これは遅すぎます。速くする方法は2つあります。

クエリのコンパイル

SQLを受け取るたびに、そのクエリ専用のコードを生成し、マシンコードにコンパイルして実行する。JVMのJITコンパイルに似ている。

ベクター処理

インタプリタのままだが、1行ずつではなく、列の値をまとめて処理する。「等しいか」「AND」のような決まった演算が組み込まれていて、列を渡すと結果がまとめて返る。

どちらも実際に使われています。速い理由は、いまのCPUの得意な形に合わせているからです。

  • メモリを順番に読む。あちこち飛ばないので、キャッシュミスが減る。
  • 小さなループに処理を集める。分岐予測が外れにくい。
  • 複数のスレッドやSIMD命令で、並列に処理する。
  • 圧縮したままのデータを直接扱う。展開やコピーの手間がない。

4.2.4マテリアライズドビューとデータキューブ

マテリアライズドビューは、クエリの結果を実際に計算して、ディスクに保存しておいたものです。普通のビュー（仮想ビュー）はクエリの別名にすぎず、読むたびに元のクエリが走ります。

元のデータが変わったら、保存した結果も更新しなければなりません。書き込みは重くなりますが、同じクエリを何度も実行するなら読み取りが速くなります。2章のタイムラインと同じ、「書くときに働いて、読むときに楽をする」形です。

その一種がデータキューブ（OLAPキューブ）です。SUM や COUNT の結果を、ディメンションの組み合わせごとに先に計算して、格子の形で持っておきます。

良い点

決まった形のクエリがとても速い。「昨日の店舗ごとの売上」は、合計のマスを見るだけ。数百万行を読まなくて済む。

悪い点

融通がきかない。「100ドル以上の商品が売上の何割か」は出せない。価格がディメンションに入っていないから。

だから、ほとんどのデータウェアハウスは生データをできるだけ残し、データキューブは特定のクエリを速くする手段としてだけ使います。

4.3多次元インデックスと全文検索

BツリーとLSMツリーは、1つの属性の範囲で探すのが得意です。でも、それだけでは足りないことがあります。

連結インデックス

複数の列をつなげて1つのキーにしたものが連結インデックスです。紙の電話帳と同じで、（姓、名）の順に並んでいます。

補足（本にはない）

INDEX (a, b) が WHERE b = ? だけのクエリに効かない、というおなじみの話は、この並び順が理由です。

多次元インデックス

地図アプリで、いま見えている四角い範囲のレストランを探すとします。緯度と経度の両方の範囲で絞る必要があります。

SELECT * FROM restaurants
WHERE latitude  > 51.4946
  AND latitude  < 51.5079
  AND longitude > -0.1162
  AND longitude < -0.1004;

両方を同時に絞れるのが多次元インデックスです。

  • 空間充填曲線。2次元の位置を1つの数に変換して、普通のBツリーで扱います。
  • Rツリー、Bkdツリー。近くの点が同じ部分木にまとまるように空間を区切る、専用の索引です。PostGISはRツリーを使います。

地図以外にも使えます。色（赤、緑、青）の範囲で商品を探す。（日付、気温）で「この年に25〜30℃だった観測」を探す、などです。

4.3.1全文検索

文章の中のどこかにあるキーワードで探すのが全文検索です。考え方としては、これも多次元の検索です。単語1つが1つの次元で、その単語を含む文書は1、含まない文書は0。「赤い リンゴ」で探すのは、「赤い」が1で、同時に「リンゴ」も1の文書を探すことです。

これに使うデータ構造が転置インデックスです。キーが単語、値が「その単語を含む文書のIDのリスト」です。このリストをポスティングリストと呼びます。

文書IDが連番なら、リストをビットマップで持てます。すると「両方の単語を含む文書」は、4.2.3と同じビットマップのANDで出せます。

ElasticsearchやSolrが使っているLuceneは、この方式です。単語からリストへの対応をSSTableのような並んだファイルに持ち、裏でマージします。ここにもログ構造化が出てきます。PostgreSQLのGINインデックスも、ポスティングリストを使います。

単語に区切らない方法：n-gram

文章を単語に区切る代わりに、n文字の切れ端を全部取り出す方法もあります。hello の3文字の切れ端（トリグラム）は hel、ell、llo です。これを転置インデックスにすれば、3文字以上のどんな部分文字列でも探せます。正規表現の検索にも使えます。欠点は、インデックスが大きくなることです。

本は、単語の間に空白がないアジアの言語では、単語に区切るだけでも専用のモデルが要ると書いています。日本語がその例です。

タイプミスへの対応

Luceneは、編集距離が一定以内の単語も探せます。編集距離1とは、1文字の追加、削除、置き換えのことです。単語の集まりをトライに似た構造で持ち、それをレーベンシュタインオートマトンというものに変換して探します。

4.3.2ベクトル埋め込み

全文検索は、同じ単語が出てこないと見つけられません。ヘルプに「サブスクリプションのキャンセル」というページがあっても、「アカウントの閉じ方」や「契約の解除」で探した人には届きません。言葉は違っても、意味は近いのに、です。

意味で探すのがセマンティック検索です。検索結果をLLMに渡して答えさせるRAG（検索拡張生成）でも使われます。

仕組みはこうです。埋め込みモデルに文書を渡すと、数字の並び（ベクトル）が返ってきます。これがベクトル埋め込みです。意味が似た文書ほど、近いベクトルになるように作られています。

実際のベクトルは、1,000個を超える数字でできていることが多いです。1つひとつの数字の意味は、考えなくてかまいません。近いか遠いかだけが大事です。近さは、2点間の直線距離（ユークリッド距離）や、2つのベクトルがなす角度（コサイン類似度）で測ります。

検索するときは、クエリの文も同じモデルでベクトルにして、それに近いベクトルを持つ文書を探します。

混同注意

4.2.3の「ベクター処理」とは別の話です。あちらは「まとめて処理するデータのかたまり」。こちらは「多次元空間の中の位置を表す数字の並び」です。

近いベクトルをどう探すか

次元が多すぎて、Rツリーではうまくいきません。専用のベクトルインデックスを使います。本は3種類を挙げています。

1. 階層なしインデックス（flat）。全部のベクトルと距離を測ります。正確ですが、遅い方法です。

2. IVFインデックス。ベクトルをあらかじめいくつかの組（パーティション）に分けておき、クエリに近い組だけを調べます。速くなりますが、結果は近似です。本当に近いベクトルが、隣の組に入っていることがあるからです。調べる組の数（プローブ）を増やすと、正確になる代わりに遅くなります。

3. HNSWインデックス。点の数が違う層を、いくつも重ねます。上の層は点が少なく、下の層ほど多くなります。各層の中では、近い点同士が線でつながっています。まず上の層で大まかに近づき、同じ点から下の層へ降りて、もっと近い点へ移る。これを一番下まで繰り返します。これも近似です。

FacebookのFaissや、PostgreSQLのpgvectorは、IVFとHNSWの両方に対応しています。

4.4まとめ

  1. データベースの仕事は、しまうことと取り出すこと。インデックスは読みを速くし、書きを遅くする。
  2. OLTP向けには2つの流派がある。ログ構造化（LSMツリー）はファイルを書き換えず、足してマージする。書き込みに強い。同一位置更新（Bツリー）は固定サイズのページをその場で書き換える。読み取りに強い。
  3. 分析向けは列指向。使う列だけ読み、圧縮し、コンパイルやベクター処理でCPUを無駄なく使う。
  4. 複数の条件を同時に絞るには、多次元インデックス、転置インデックス、ベクトルインデックスを使う。
  5. 「追記してマージする」ログ構造化は、LSMツリーだけでなく、列指向の書き込みにもLuceneにも出てくる。

理解度チェック

答えを頭の中で言ってから、開いて確かめてください。

1. インデックスを増やすと何が良くなり、何が悪くなる？

読み取りが速くなります。代わりに、書くたびにインデックスも更新するので書き込みが遅くなり、ディスクも余分に使います。

2. SSTableは、なぜ全部のキーを索引に入れなくていい？

キー順に並んでいるからです。各ブロックの最初のキーだけ覚えておけば、探すキーがどのブロックにあるかがわかります。あとはそのブロックを順に読むだけです。

3. LSMツリーで、存在しないキーの読み取りが遅くなりやすいのはなぜ？ 何で和らげる？

メムテーブルから古いセグメントまで、順に全部調べることになるからです。ブルームフィルタで「このセグメントには絶対にない」とわかれば、読まずに飛ばせます。

4. ブルームフィルタの「ない」と「ある」、信じていいのはどっち？

「ない」は確実です。「ある」は、ほかのキーのビットとたまたま重なっただけの偽陽性かもしれません。その場合は実際に読んで確かめます。

5. Bツリーでページ分割の途中に落ちると何が困る？ どう防ぐ？

一部のページだけ書かれて、木が壊れます。変更を先にWAL（先行書き込みログ）へ追記しておき、落ちたあとはそれを読んで正しい状態に戻します。

6. SSDには動く部品がないのに、なぜシーケンシャルライトが有利？

消去がブロック単位でしかできないからです。散らばった書き込みでは、ブロックの中に要るページと要らないページが混ざり、引っ越し（GC）が増えます。まとめて書けば、ブロックを丸ごと消去できます。

7. インメモリデータベースが速い本当の理由は？

ディスクを読まないからではありません。メモリ上のデータ構造を、ディスクに書ける形へ変換する手間がないからです。

8. 列指向で、列ごとに別々に並べ替えてはいけないのはなぜ？

各列のk番目が同じ行、という対応で行を復元しているからです。別々に並べ替えると、どの値が同じ行のものかわからなくなります。

9. データキューブの弱点は？

先に決めたディメンション以外の切り口では答えられないことです。だから生データも残しておきます。

10. 緯度と経度の連結インデックスでは、四角い範囲の検索がなぜ遅い？

先頭の列（緯度）でしか絞れないからです。緯度の帯に入る点を、経度に関係なく全部読むことになります。両方を同時に絞るには、Rツリーのような多次元インデックスが要ります。

11. IVFやHNSWの結果が「近似」なのはなぜ？

全部のベクトルとは比べないからです。速さと引き換えに、本当にいちばん近いベクトルを見逃すことがあります。
