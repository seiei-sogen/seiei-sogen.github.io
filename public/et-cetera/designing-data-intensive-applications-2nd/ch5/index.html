5章 エンコーディングと発展性

アプリは変わり続けます。でも、全部をいっせいに新しくすることはできません。だから、古いコードと新しいコード、古いデータと新しいデータが混ざって動く時間が必ずあります。5章は、その間も壊れないようにデータを詰める方法の話です。

ひとことで

データをバイト列に詰める形式を選ぶことは、「あとからどれだけ楽に変更できるか」を選ぶことです。合言葉は2つ。後方互換性（新しいコードが古いデータを読める）と、前方互換性（古いコードが新しいデータを読める）。

色の約束です。琥珀は古いもの、青緑は新しいもの、藤色はスキーマ（データの設計図）とその目印、朱は問題。最後まで同じ意味で使います。

5.0なぜ新旧が混ざるのか

コードは一瞬では入れ替わらない

データの形を変えると、たいていコードも変えます。たとえばレコードにフィールドを1つ足して、コードがそれを読み書きし始める、という具合です。

ところが大きなアプリでは、コードの入れ替えは一瞬では終わりません。本は理由を2つ挙げています。

  • サーバー側：逐次更新をするから。新しいバージョンを数台ずつ入れて、問題がないか見ながら広げていきます。サービスを止めずにリリースできるので、こまめに出せるようになります。
  • クライアント側：ユーザーしだいだから。アップデートを入れるかどうかはユーザーが決めます。古いアプリがしばらく残ります。

互換性は2方向ある

新旧が混ざっても動き続けるには、2つの向きの互換性が要ります。

後方互換性は、ふつうそれほど難しくありません。新しいコードを書く人は、古いデータの形を知っているからです。最悪、古いデータを読むための古いコードを残しておけば済みます。

前方互換性は厄介です。古いコードは、未来に何が足されるかを知りようがありません。「知らない部分は無視する」ように、最初から作っておく必要があります。

補足（覚え方。本にはない）

主語はどちらも「読む側のコード」です。後方は後ろ、つまり過去を向いています。過去のデータが読める。前方は前、つまり未来。未来のデータが読める。こう覚えると混ざりません。

APIではどうなるか

APIでは、リクエストとレスポンスで「書く人」と「読む人」が入れ替わります。古いクライアントが新しいサービスを呼ぶ場合はこうです。

逆に、新しいクライアントが古いサービスを呼ぶなら、リクエストに前方互換性、レスポンスに後方互換性が要ります。

知らないフィールドを消してしまう事故

前方互換性には、もう1つ落とし穴があります。古いコードが「読むだけ」でなく「読んで、直して、書き戻す」ときです。

望ましいのは、古いコードが意味のわからないフィールドもそのまま持ち続けて、書き戻すときに返すことです。レコードを、知らないフィールドを持てない入れ物（決まったプロパティだけのオブジェクトなど）に移し替えると、この事故が起きます。

この章で見ていくこと

JSON、XML、Protocol Buffers、Avroなどの形式が、それぞれスキーマの変更をどう扱うか。そして、その形式がデータベース、サービス、ワークフロー、メッセージングでどう使われるか。この2本立てです。

5.1データのエンコーディング形式

プログラムは、データを少なくとも2つの姿で扱います。

  • メモリの中。オブジェクト、配列、ハッシュテーブル、ツリーなど。CPUが速く触れるように作られていて、ふつうポインタでつながっています。
  • ファイルやネットワークの上。それだけで完結した、ひと続きのバイト列。ポインタは別のプロセスにとって意味がないので、メモリの中とはかなり違う形になります。
用語：呼び名がたくさんある

メモリ → バイト列は、エンコーディング、シリアライゼーション、マーシャリング。全部同じ意味です。逆のバイト列 → メモリは、デコーディング、パース、デシリアライゼーション、アンマーシャリング。

「シリアライゼーション」はトランザクションの章（8章）でまったく別の意味で出てきます。まぎらわしいので、本は「エンコーディング」で統一しています。

補足（本にはない例）

JavaScriptなら、JSON.stringify() がエンコード、JSON.parse() がデコードです。毎日やっているあれです。

変換がいらない場合もあります。データベースが圧縮したままのデータを直接あつかう場合（4章）や、Cap'n Proto、FlatBuffersのようなゼロコピーの形式です。これらはメモリの中でもディスクの上でも同じ形で使えるように作られています。でも、ほとんどのシステムでは変換が要ります。

5.1.1言語固有のフォーマット

多くの言語には、オブジェクトをそのままバイト列にする機能が最初から付いています。Javaの java.io.Serializable、Pythonの pickle、Rubyの Marshal などです。数行書くだけで保存と復元ができて便利です。でも、深刻な問題が4つあります。

  1. その言語に縛られる。別の言語から読むのが難しくなります。この形式で保存すると、長いあいだ今の言語から離れられません。他の組織のシステムともつなぎにくくなります。
  2. セキュリティの穴になる。元と同じ型で復元するには、デコードする側が好きなクラスを生成できる必要があります。攻撃者が細工したバイト列を読ませれば、好きなクラスを動かせます。リモートからコードを実行される攻撃につながります。
  3. バージョン管理が後回し。手軽さが目的なので、前方・後方互換性はないがしろにされがちです。
  4. 効率も後回し。Javaの組み込みシリアライゼーションは、遅くてサイズが大きいことで悪名高いです。
本の結論

言語に組み込みのエンコーディングは、ごく一時的な用途以外では使わないほうがよい。

5.1.2JSON、XML、CSV

どの言語からも読み書きできる標準の形式といえば、JSONとXMLです。CSVも人気ですが、入れ子のない表の形しか表せません。3つともテキストなので、人間もいちおう読めます。

見た目の好みは別として、中身の問題がいくつかあります。

問題1：数値があいまい

XMLとCSVは、「数値」と「たまたま数字だけの文字列」を区別できません。JSONは文字列と数値を区別しますが、整数と小数は区別しません。精度も決めていません。

これは大きな数で事故になります。253より大きい整数は、倍精度の浮動小数点数では正確に表せません。JavaScriptのように数値をすべて浮動小数点数で持つ言語でパースすると、値がずれます。

X（旧Twitter）の投稿IDは64ビットの数値です。そこでXのAPIは、同じIDをJSONの数値として1回、10進数の文字列として1回、合計2回入れて返します。JavaScriptのアプリは文字列のほうを使えば、ずれません。

問題2：バイナリを入れられない

JSONとXMLは、人間が読む文字列（Unicode）は得意です。でも、画像のような生のバイト列は入れられません。そこで、Base64でバイナリをテキストに変えて入れるのが定番です。動きはしますが、場当たり的で、サイズも増えます。

問題3：スキーマが複雑か、そもそも無い

XML SchemaとJSON Schemaは強力ですが、そのぶん覚えるのも実装するのも大変です。使わない場合は、正しい読み方をアプリのコードに直接書くことになります。

CSVにはスキーマがありません。各行、各列の意味はアプリが決めます。列が増えたら手で対応します。エスケープのルールは仕様があるのに、正しく実装していないパーサーもあります。

それでも使われ続ける

欠点はあっても、JSON、XML、CSVは多くの用途に十分です。とくに組織と組織のあいだでデータを渡す形式としては、これからも人気でしょう。そういう場面では、形式のきれいさや効率よりも、相手と何か1つに合意できることのほうがずっと難しくて大事だからです。

5.1.2.1JSON Schema

JSON Schemaは、JSONの形を決めるためのスキーマ言語です。いろいろな場所で使われています。

  • WebサービスのAPI定義（OpenAPIの一部として）
  • スキーマレジストリ（ConfluentのSchema Registry、Red HatのApicurio Registry）
  • データベース（PostgreSQLのpg_jsonschema拡張、MongoDBの $jsonSchema）

string、number、integer、object、array、boolean、nullといった基本の型に加えて、値の制約も書けます。たとえば「port は1以上65535以下」です。

知っておくべきは、スキーマに書いていないフィールドの扱いです。

既定はオープンです。なのでJSON Schemaはふつう、「定義したフィールドに変な値が入るのを禁じる」ものです。「何が入ってよいか」を全部決めるものではありません。

次は本の例です。「整数のIDから文字列へのマップ」を表したい。でもJSONのキーは必ず文字列です。そこで「キーは数字だけ、値は文字列だけ、それ以外は不可」と制約をかけます。

{
  "$schema":
    "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "patternProperties": {
    "^[0-9]+$": { "type": "string" }
  },
  "additionalProperties": false
}

ほかにも、条件分岐、名前つきの型、別の場所にあるスキーマへの参照など、機能は豊富です。そのぶん定義が扱いにくくなりがちで、互換性を保ったままスキーマを変えていくのが難しいことがあります。XML Schemaも同じです。

5.1.2.2バイナリのJSON

JSONはバイナリ形式に比べて場所を取ります。そこで、JSONをバイナリにした形式がたくさん作られました。MessagePack、CBOR、BSONなどです。

ここから先、本は次のレコードをいろいろな形式に詰めて、大きさを比べます。空白を取ると、テキストのJSONで81バイトです。

{
  "userName": "Martin",
  "favoriteNumber": 1337,
  "interests": ["daydreaming", "hacking"]
}

MessagePackで詰めてみます。まず先頭の2バイトの読み方です。

長さを先に書くので、文字列の終わりを示す記号やエスケープがいりません。全体はこうなります。

66バイト。81バイトから少し減っただけです。理由は図のとおりで、スキーマを持たない形式はフィールド名を毎回データの中に入れるしかないからです。

この程度の節約のために人間が読めなくなるのは、割に合うか微妙です。次は、同じレコードを半分のバイト数にする方法を見ます。

5.1.3Protocol Buffers

Protocol Buffers（protobuf）は、Googleが作ったバイナリ形式です。Facebook生まれのApache Thriftとよく似ていて、ここでの話はほぼThriftにも当てはまります。

Protocol Buffersでは、先にスキーマを書きます。

syntax = "proto3";

message Person {
  string user_name = 1;
  int64 favorite_number = 2;
  repeated string interests = 3;
}

このスキーマをツールに渡すと、いろいろな言語用のクラスを生成してくれます。アプリはそのクラスを呼んで、エンコードとデコードをします。書けるのはフィールドと型だけで、JSON Schemaのような値の制約は書けません。そのぶんシンプルです。

さっきのレコードを詰めると、33バイトになります。

MessagePackとの違いは1つ。フィールド名（userName など）がありません。代わりに、スキーマに書いた = 1、= 2、= 3 の番号が入っています。これがフィールドタグです。

補足（本にはないたとえ）

タグ番号は、スポーツ選手の背番号のようなものです。データには背番号しか書いてありません。「7番は誰か」は、選手名簿（スキーマ）を見ればわかります。

数値の詰め方にも工夫があります。可変長整数です。

もう1つ。Protocol Buffersには「リスト」という型がありません。repeated と書いたフィールドは、同じタグ番号を何度もくり返すことでリストを表します。上の33バイトの図で、1a（タグ番号3）が2回出てくるのがそれです。

5.1.3.1タグ番号とスキーマの進化

スキーマは時間とともに変わります。これをスキーマの進化と呼びます。Protocol Buffersは、互換性を保ったまま、どう変更を受け止めるのでしょうか。

エンコードされたレコードは、フィールドを順につなげただけのものです。各フィールドはタグ番号で見分けます。値が入っていないフィールドは、単に省略されます。ここから大事なルールが出てきます。

いちばん大事なルール

フィールドの名前は変えてよい。データに名前は入っていないからです。フィールドのタグ番号は変えてはいけない。変えると、これまでに書いたデータが全部読めなくなります。

フィールドを足すときは、新しいタグ番号を付けます。

図5-1の「知らないフィールドが消える」事故も、これで避けられます。

フィールドを消すときは、足すときの逆です。気をつけるのは、消したタグ番号を二度と使わないこと。その番号の入った古いデータがどこかに残っているかもしれないからです。うっかり再利用しないよう、スキーマに「予約済み」と書いておけます。

型を変えるときは、できる組み合わせもありますが、値が切り捨てられる危険があります。

逆向き、つまり新しいコードが古い32ビットのデータを読むのは問題ありません。足りない上のビットを0で埋めればよいからです。

5.1.4Avro

Apache Avroも、スキーマを使うバイナリ形式です。2009年にHadoopのサブプロジェクトとして始まりました。Protocol BuffersがHadoopの使い方に合わなかったためです。

スキーマの書き方は2つあります。人間が書きやすいAvro IDLと、機械が読みやすいJSON形式です。IDLで書くとこうなります。

record Person {
  string userName;
  union { null, long } favoriteNumber = null;
  array<string> interests;
}

Protocol Buffersと見比べてください。タグ番号がありません。このスキーマで同じレコードを詰めると、32バイト。ここまでで最小です。

値を順番につなげただけです。文字列は「長さ、そのあと中身」と並んでいますが、それが文字列だという印はどこにもありません。整数かもしれないし、別の何かかもしれません。

では、どうやって読むのか。答えは「スキーマを見ながら読む」です。

ここが弱点に見える

読む側が、書いた側とまったく同じスキーマを知らないと、正しく読めません。少しでも食い違うと、でたらめな値になります。

補足（本にはないたとえ）

答えだけを順番に書いた解答用紙のようなものです。問題用紙（スキーマ）がなければ、「Martin」が何の質問への答えなのかわかりません。

これでどうやってスキーマを変えていくのでしょうか。

5.1.4.1書き手のスキーマと読み手のスキーマ

Avroは、スキーマを2つ使い分けます。

  • ライタースキーマ（書き手のスキーマ）：データを詰めたときに使ったスキーマ。
  • リーダースキーマ（読み手のスキーマ）：読むアプリが「こういうフィールドがほしい」と思っているスキーマ。

読むときは、この両方を使います。書き手のスキーマでバイト列を正しく切り分けて、それを読み手のスキーマの形に変換します。

2つが同じなら、そのまま読むだけです。違うときは、Avroが2つを見比べて、差を埋めてくれます。

5.1.4.2スキーマの進化のルール

Avroでは、互換性をこう言い換えられます。前方互換性は、書き手のスキーマが読み手より新しくてもよいこと。後方互換性は、書き手のスキーマが読み手より古くてもよいこと。

細かい注意がいくつかあります。

  • nullは勝手には入らない。nullを許したいフィールドは、union { null, long } のようにユニオン型で書きます。少し面倒ですが、何がnullになりうるかがはっきりして、バグが減ります。nullをデフォルト値にできるのは、nullがユニオンの最初に書いてあるときだけです。
  • 型の変更は、Avroが変換できる組み合わせなら可能です。
  • 名前の変更は、読み手のスキーマに別名（エイリアス）を書けばできます。ただし後方互換だけで、前方互換にはなりません。
  • ユニオンに選択肢を足すのも、後方互換だけです。

5.1.4.3書き手のスキーマをどうやって知るのか

ここまで、大事な疑問を飛ばしていました。読む側は、そのデータを書いたときのスキーマをどうやって手に入れるのでしょうか。

レコードごとにスキーマを丸ごと付けるのは論外です。スキーマのほうがデータより大きくなって、せっかくの節約が消えます。答えは、使う場面によって変わります。

  1. 大きなファイル。同じスキーマのレコードが何百万件も入ったファイルなら、先頭に1回書けば済みます。Avroはそのためのファイル形式（オブジェクトコンテナファイル）を決めています。
  2. データベース。レコードごとに書いた時期が違い、スキーマも違うかもしれません。そこで各レコードの頭に版番号を付け、版ごとのスキーマの一覧を別に持ちます。ConfluentのKafka用スキーマレジストリや、LinkedInのEspressoがこの方式です。
  3. ネットワーク接続。つないだときに、使うスキーマの版を相談して決めます。あとは切れるまでそれを使います。Avro RPCがこの方式です。

スキーマの版の一覧は、どのみち持っておくと便利です。ドキュメントになりますし、互換性を機械的にチェックできます。版番号は、連番でも、スキーマのハッシュでもかまいません。

5.1.4.4動的に作るスキーマ

タグ番号がないことは、何がうれしいのでしょうか。答えは、スキーマを機械に作らせやすいことです。

たとえば、リレーショナルデータベースの中身をファイルに書き出したいとします。

テーブルの列が1つ増えて1つ減っても、新しいテーブル定義から新しいAvroスキーマを作って書き出すだけです。書き出す処理は、スキーマが変わったことを気にしなくてかまいません。読む側は名前で対応づけるので、古い読み手のスキーマとも照合できます。

動的に作るスキーマは、Avroが最初から想定していた使い方です。Protocol Buffersの設計目標には入っていませんでした。

5.1.5スキーマの利点

Protocol BuffersとAvroのスキーマ言語は、XML SchemaやJSON Schemaよりずっとシンプルです。値の細かい制約は書けませんが、そのぶん実装しやすく、多くの言語で使えるようになりました。

スキーマを使うバイナリ形式には、小ささ以外にも良いところがあります。

  1. コンパクト。フィールド名を入れなくてよいので、「バイナリのJSON」よりずっと小さくなります。
  2. 腐らないドキュメント。スキーマがないとデコードできないので、スキーマは必ず最新です。人が手で書いた説明書は、すぐ現実とずれます。
  3. デプロイ前に互換性を調べられる。スキーマの一覧を持っておけば、変更が前方・後方互換かを機械で確かめられます。
  4. 型チェックが効く。スキーマからコードを生成できるので、静的型付けの言語ならコンパイル時に間違いを見つけられます。
Protocol Buffers
  • フィールドはタグ番号で見分ける
  • データに目印が入っている
  • 番号は人が管理する
Avro
  • フィールドは名前で対応づける
  • データに目印は入っていない
  • スキーマを機械で作りやすい

ちなみに、この考え方は新しくありません。1984年に標準化されたASN.1というスキーマ言語がすでに、タグ番号によるスキーマの進化を持っていました。SSL証明書（X.509）のエンコードに今も使われています。ただし複雑で資料も乏しく、新しく使うものではないと本は言います。

また、多くのデータベースは独自のバイナリ形式を持っています。クエリと結果をやり取りするネットワークプロトコルがそれで、ドライバ（ODBCやJDBC）がデコードしてくれています。

5.1のまとめ

スキーマの進化は、スキーマレスなJSONデータベースと同じ種類の柔軟さをくれます。そのうえ、データについての確かな保証と、よい道具も付いてきます。ただし運用を楽にするため、同時に使うスキーマ形式の数は最小限にしよう、と本は勧めています。

5.2データフローのモード

互換性とは、データを詰めるプロセスとそれを開けるプロセスのあいだの関係です。では実際には、誰が詰めて、誰が開けるのでしょうか。データの流れ方ごとに見ていきます。

本はこの3つに加えて、サービス呼び出しをいくつもつなげる「ワークフロー」も取り上げます。順番に行きます。

5.2.1データベースを介したデータフロー

データベースでは、書くプロセスが詰めて、読むプロセスが開けます。プロセスが1つしかない場合でも、読むのは「あとの時点の自分」です。

ただし、ふつうはデータベースを使うプロセスは1つではありません。同じサービスが何台も並んで動いています。逐次更新の途中なら、新しいコードの台と古いコードの台が混ざっています。

つまりデータベースでは、後方互換性も前方互換性も、両方要ることが多いのです。図5-1の「知らないフィールドを消す事故」が起きるのも、この場面です。

5.2.1.1データはコードより長生きする

データベースの中には、5ミリ秒前に書いた値もあれば、5年前に書いた値もあります。

全部のデータを新しいスキーマに書き直す（マイグレーションする）こともできます。でもデータが大きいと高くつきます。そこで多くのデータベースは、書き直しを先延ばしにします。

  • LSMツリーのストレージエンジン（4章）は、コンパクションのついでに最新の形式で書き直します。
  • 多くのリレーショナルデータベースは、「デフォルトがnullの列を足す」程度の変更なら、既存の行に触りません。

これもスキーマの進化の一種です。ディスクの上にはいろいろな時代の形式が混ざっていても、データベース全体が1つのスキーマでできているように見せられます。

補足（本にはない話）

PostgreSQLで、NULLを許す列を ALTER TABLE … ADD COLUMN で足すと、巨大なテーブルでもすぐ終わります。行を書き換えていないからです。

もっと込み入った変更、たとえば「1つの値だった属性を複数の値にする」「一部のデータを別のテーブルに移す」は、やはりデータの書き直しが要ります。多くはアプリ側でやることになります。

5.2.1.2アーカイブストレージ

バックアップやデータウェアハウスへの取り込みのために、データベースのスナップショットを取ることがあります。このとき、元のデータベースにいろいろな時代の形式が混ざっていても、書き出すデータはふつう最新のスキーマにそろえます。どうせ全部コピーするのだから、そろえたほうが合理的です。

書き出したデータは、一度に書かれて、あとは変わりません。なので、Avroのオブジェクトコンテナファイルがよく合います。Parquetのような分析向けの列指向形式（4章）にする良い機会でもあります。

5.2.2サービスを介したデータフロー：RESTとRPC

ネットワーク越しの通信でいちばんよくある形は、役割を2つに分けることです。サーバーがAPIを公開し、クライアントがそこへリクエストを送ります。サーバーが公開するAPIをサービスと呼びます。Webがまさにこの形です。

サービスはデータベースに少し似ています。データを送れて、問い合わせもできます。違いは自由度です。データベースはクエリ言語で好きな問い合わせができます。サービスは、あらかじめ決めた入力と出力しか受け付けません。この制限のおかげで、クライアントにできることを細かく決められます（カプセル化）。

マイクロサービスの大事な目標は、サービスを別々にデプロイして、別々に変えていけることです。1つのサービスは1つのチームが持ち、他のチームと相談せずにどんどんリリースできるのが理想です。ということは、新旧のサーバーとクライアントが同時に動いているのが当たり前です。だからAPIのバージョン間の互換性が要ります。

5.2.2.1Webサービス

サービスとの通信にHTTPを使うとき、それをWebサービスと呼びます。

いちばん人気のある設計の考え方がRESTです。HTTPの原則に乗っかります。シンプルなデータ形式を使い、リソースをURLで指し、キャッシュ制御や認証にHTTPの機能をそのまま使います。この原則に沿ったAPIをRESTfulと呼びます。

サービスを呼ぶ側は、どのエンドポイントに、どんな形式で送り、何が返るかを知らなければなりません。それを書き表すのがインターフェース定義言語（IDL）です。人気があるのは2つです。

  • OpenAPI（Swaggerとも呼ぶ）：JSONをやり取りするWebサービス向け。
  • Protocol Buffers：gRPCサービス向け。5.1.3で見たスキーマをそのまま使います。

OpenAPIの定義は、JSONかYAMLで書きます。本の例を短くするとこうです。

openapi: 3.0.0
info:
  title: Ping, Pong
  version: 1.0.0
paths:
  /ping:
    get:
      summary: Given a ping, returns a pong
      responses:
        '200':
          description: A pong
          content:
            application/json:
              schema:
                type: object
                properties:
                  message:
                    type: string

API呼び出しを受けるコードは、Spring Boot、FastAPI、gRPCといったサービスフレームワークで書くのがふつうです。ルーティング、メトリクス、キャッシュ、認証などはフレームワークが受け持ち、開発者は各エンドポイントの処理に集中できます。

IDLの道具は、コード生成のほかに、ドキュメントの生成、スキーマ変更の互換性チェック、ブラウザから試し打ちできる画面の提供もしてくれます。

5.2.2.2リモートプロシージャコール（RPC）の問題点

Webサービスは、ネットワーク越しにAPIを呼ぶ技術の、長い歴史のいちばん新しい姿です。昔の技術には深刻な問題がありました。

  • EJBとRMI：Javaでしか使えない。
  • DCOM：Microsoftのプラットフォームでしか使えない。
  • CORBA：複雑すぎるうえ、前方互換も後方互換もない。
  • SOAPとWS-*：ベンダー間でつながることを目指したが、やはり複雑で互換性に苦しんだ。

これらはみな、1970年代に生まれたRPCのアイデアに基づいています。RPCは、遠くのサービスへのリクエストを、同じプロセス内の関数呼び出しと同じに見せようとします。この「場所を意識させない」性質をロケーション透過性と呼びます。

便利そうですが、根本的に無理があります。ネットワーク越しのリクエストは、ローカルの関数呼び出しとは別物だからです。

ローカルの関数は、渡した引数しだいで成功か失敗かが決まります。予測できます。ネットワークは違います。リクエストが途中で消える、相手のマシンが遅い、落ちている。どれも自分ではどうにもできません。

返事がないからといってリトライすると、別の問題が起きます。

ローカルの関数呼び出しに、こんな心配はありません。違いはまだあります。

  • かかる時間が読めない。ローカルの関数は毎回ほぼ同じ時間で終わります。ネットワークは、調子がよければ1ミリ秒未満、混んでいれば同じ処理に数秒かかります。
  • ポインタを渡せない。ローカルならメモリ上のオブジェクトへの参照を渡すだけです。ネットワーク越しでは、引数を全部バイト列に詰めて送ります。数値や短い文字列ならよいのですが、大きなデータや書き換えられるオブジェクトではすぐ困ります。
  • 言語が違うかもしれない。クライアントとサービスが別の言語なら、型を変換しなければなりません。JavaScriptが253より大きい数を扱えない、あの問題がここでも出ます。
本の結論

遠くのサービスを、手元のオブジェクトのように見せかけても意味がありません。根本的に違うものだからです。RESTが好まれる理由の1つは、ネットワーク越しのやり取りを、関数呼び出しとは別物として正直に扱うところにあります。

補足（本にはないたとえ）

ローカルの関数呼び出しは、隣の席の人に声をかけるようなものです。聞こえたかどうかは見ればわかります。ネットワーク越しは、手紙です。返事が来ないとき、届かなかったのか、相手が読んで動いたのに返事が迷子になったのか、こちらからはわかりません。

5.2.2.3ロードバランサー、サービスディスカバリ、サービスメッシュ

サービスを呼ぶには、相手のアドレスを知らなければなりません。これをサービスディスカバリの問題と呼びます。

いちばん単純なのは、クライアントの設定にIPアドレスとポートを直接書くことです。動きはします。でも、サーバーが落ちたり、別のマシンに移ったり、混んだりするたびに、手で書き直すことになります。

実際には、同じサービスを何台ものマシンで動かして、リクエストを振り分けます。これが負荷分散です。方法がいくつかあります。

  • ハードウェアロードバランサー。データセンターに置く専用の機器です。
  • ソフトウェアロードバランサー。NGINXやHAProxyなど。やることはほぼ同じですが、専用の機器がいらず、ふつうのマシンに入れて使えます。
  • DNS。1つのドメイン名に複数のIPアドレスを結びつけて、振り分けます。弱点は、DNSがもともと「変更をゆっくり広める」「結果をキャッシュする」作りであること。サーバーの入れ替わりが激しいと、クライアントがもう存在しない古いIPアドレスを見てしまいます。

サービスディスカバリシステムは、DNSの代わりに、etcdやApache ZooKeeperのような名簿係（レジストリ）を使います。

DNSに比べて、インスタンスが頻繁に入れ替わる環境に強くなります。名簿には、データセンターの場所などの追加情報も載せられます。クライアントはそれを見て、より賢く接続先を選べます。

サービスメッシュは、ソフトウェアロードバランサーとサービスディスカバリを組み合わせた、手の込んだ方式です。

複雑ですが、見返りがあります。アプリとサイドカーのあいだは同じマシン内の接続なので、通信の暗号化はサイドカーに任せきりにできます。アプリは証明書やTLSを気にしなくて済みます。どのサービスがどのサービスを呼んでいるか、どこで失敗しているかも、メッシュがまとめて見せてくれます。

Kubernetesなどで、入れ替わりの激しい環境
サービスメッシュ（Istio、Linkerdなど）を選ぶことが多い
データベースやメッセージングなど特殊な基盤
専用に作られたロードバランサーが要ることがある
もっとシンプルな構成
ソフトウェアロードバランサーが最適

5.2.2.4RPCでのエンコーディングと進化

サービスの場合、データベースより話が少し単純になります。「サーバーを全部先に更新して、クライアントはあとから更新する」と決めてしまえるからです。

互換性の性質は、使っているエンコーディングからそのまま引き継がれます。

  • gRPC（Protocol Buffers）とAvro RPCは、それぞれの形式のルールに従って進化させられます。
  • RESTful APIは、たいていJSONです。「省略できるリクエストパラメータを足す」「レスポンスに新しいフィールドを足す」は、ふつう互換性を壊さない変更とされます。

難しいのは、組織の境界をまたぐときです。サービスを出す側は、よその会社のクライアントにアップグレードを強制できません。だから互換性を長いあいだ、ことによると無期限に保つことになります。どうしても壊す変更が要るときは、APIの複数のバージョンを並べて動かし続けることになりがちです。

クライアントが「どのバージョンを使いたいか」を伝える方法に、決まった正解はありません。RESTful APIでは、URLかHTTPの Accept ヘッダーにバージョン番号を入れるのが一般的です。APIキーでクライアントを見分けるサービスなら、クライアントごとの希望バージョンをサーバー側に保存しておく手もあります。

5.2.3耐久性のある実行とワークフロー

サービスを分けると、1つの仕事をするのに、いくつものサービスを順番に呼ぶことになります。本の例は決済です。

用語

この一連のステップをワークフロー、1つ1つのステップをタスクと呼びます。タスクの呼び名は製品によって違います。Temporalではアクティビティ、ほかに耐久関数と呼ぶものもあります。中身は同じです。

ワークフローを動かすのがワークフローエンジンです。どのタスクを、いつ、どのマシンで動かすか。失敗したらどうするか。いくつ並列で動かすか。それを決めます。

ワークフローエンジンにはいろいろな種類があります。

  • Airflow、Dagster、Prefect：データシステムとつながって、ETLの処理を順に動かす。
  • Camunda、Orkes：図で描く記法（BPMN）があり、エンジニアでなくてもワークフローを作れる。
  • Temporal、Restate：耐久性のある実行（durable execution）を提供する。

なぜ「耐久性」が要るのか

決済は、1件につきちょうど1回だけ処理したいものです。ところが途中で落ちると、こうなります。

1つのデータベースの中なら、2つの処理をトランザクションで包めば済みます。でもサービスが分かれていると、それができません。相手が自分たちで管理できない外部の決済サービスのこともあります。

耐久性のある実行のフレームワークは、ワークフローに厳密に1回のセマンティクス（exactly-once）を与える道具です。しくみはこうです。フレームワークが、すべてのRPC呼び出しと状態の変更を、消えないログに記録しておきます。タスクが失敗したら最初からやり直しますが、ログに残っている呼び出しは実行しません。

Temporalでは、ワークフローをふつうのコードとして書きます。本の例を短くするとこうです。execute_activity の呼び出し1つ1つが、ログに記録される単位です。

@workflow.defn
class PaymentWorkflow:
  @workflow.run
  async def run(self, payment):
    is_fraud = await workflow.execute_activity(
      check_fraud, payment, ...)
    if is_fraud:
      return PaymentResultFraudulent
    resp = await workflow.execute_activity(
      debit_credit_card, payment, ...)
    # ...

気をつけること

便利ですが、落とし穴もあります。

  • 外のサービスは冪等でないといけない。外部の決済サービスのような相手には、同じ依頼が2回届くことがありえます。呼ぶ側が一意のIDを付け忘れないようにする必要があります。
  • コードの変更に弱い。フレームワークは、やり直しのときも「同じ呼び出しが、同じ順番で」行われると期待しています。

だから、動いている途中のワークフローのコードを書き換えるより、新しいバージョンを別にデプロイするほうが安全です。すでに始まっているワークフローのやり直しは古いコードのまま、新しく始まるものだけが新しいコードを使います。これも「新旧が混ざる」の一例です。

  • 毎回同じ結果になるコードでないといけない。同じ入力なら同じ出力になること（決定的）が前提です。乱数や現在時刻を直接使うと、やり直しのたびに結果が変わって壊れます。フレームワークが用意している「決定的な版」の関数を使います。こうした間違いを見つける静的解析ツールもあります（TemporalのWorkflow Checkなど）。

5.2.4イベント駆動アーキテクチャ

最後の流れ方です。ここでは、送るものをリクエストではなくイベントまたはメッセージと呼びます。RPCと違う点が2つあります。送り手は、受け手が処理し終わるのを待ちません。そして、直接つながずにメッセージブローカーという仲介役を通します。

ブローカーを挟むと、直接のRPCに比べて良いことがあります。

  1. 受け手が落ちていたり混んでいたりしても、ブローカーがためておいてくれる。
  2. 処理中に落ちたプロセスには、メッセージを自動で届け直してくれる。
  3. 送り手が受け手のIPアドレスを知らなくてよい。サービスディスカバリがいらない。
  4. 同じメッセージを、複数の受け手に送れる。
  5. 送り手と受け手が切り離される。送り手は出すだけで、誰が受け取るかを気にしない。

この通信は非同期です。送り手は送ったら忘れてかまいません。返事がほしければ、別の通り道で返事を待つ形にして、RPCふうに使うこともできます。

5.2.4.1メッセージブローカー

昔は商用の製品が中心でした。その後、RabbitMQ、ActiveMQ、NATS、Redpanda、Apache Kafkaなどのオープンソースが広まりました。最近は、Amazon Kinesis、Azure Service Bus、Google Cloud Pub/Subのようなクラウドのサービスも使われています。くわしい比較は12章です。

ブローカーは、ふつう中身の形式に口を出しません。メッセージは、メタデータの付いたただのバイト列です。なので、どのエンコーディングでも使えます。よくあるのは、Protocol Buffers、Avro、JSONのどれかを使い、ブローカーの横にスキーマレジストリを置くやり方です。有効なスキーマの版を全部しまっておき、互換性をチェックします。メッセージ版のOpenAPIにあたるAsyncAPIで、メッセージのスキーマを書くこともできます。

メッセージをどれだけ長く持つかは、ブローカーによります。多くはディスクに書いて、落ちても失わないようにします。そして多くは、受け手が受け取ったら消します。ただ、ずっと残す設定にできるものもあります。イベントソーシング（3章）をやりたいなら、それが要ります。

ここでも同じ事故に注意

受け取ったメッセージを別のトピックへ出し直すときは、知らないフィールドを消さずに持ち回る必要があります。図5-1と同じ話です。

5.2.4.2分散アクターフレームワーク

アクターモデルは、もともと1つのプロセスの中で並行処理をするための考え方です。スレッドを直接あつかうと、競合、ロック、デッドロックに悩まされます。そこでロジックをアクターという単位に閉じ込めます。

  • アクターは、ほかと共有しない自分だけの状態を持つ。
  • ほかのアクターとは、非同期のメッセージだけでやり取りする。
  • 一度に処理するメッセージは1つだけ。だからスレッドの心配がいらない。
  • メッセージが届く保証はない。失われることもある、という前提で作る。

分散アクターフレームワーク（Akka、Orleans、Erlang/OTPなど）は、この考え方を複数のノードに広げたものです。

ロケーション透過性は、RPCよりアクターモデルのほうがうまくいきます。アクターモデルは、同じプロセスの中でさえ「メッセージは失われるかもしれない」と最初から考えているからです。ローカルとリモートの差が、もともと小さいのです。

ただし、アクターのアプリを逐次更新するなら、やはり互換性が問題になります。新しいノードから古いノードへ、またはその逆へ、メッセージが飛ぶからです。この章で見たエンコーディングのどれかを使えば解決できます。

5.3まとめと確認問題

  1. 逐次更新をすると、古いコードと新しいコードが同時に動く。止めずに出せて、まずいリリースを早く見つけて戻せる。そのかわり、流れるデータすべてに互換性が要る。
  2. 後方互換性は「新しいコードが古いデータを読める」。前方互換性は「古いコードが新しいデータを読める」。
  3. 言語固有の形式は、1つの言語に縛られ、互換性もたいてい無い。
  4. JSON、XML、CSVは広く使われる。互換性は使い方しだい。型があいまいなので、大きな数値やバイナリに注意。
  5. Protocol BuffersやAvroは、スキーマを使ってコンパクトに詰める。互換性のルールがはっきり決まっている。弱点は、デコードしないと人間が読めないこと。
  6. データの流れ方は、データベース、サービス（RESTとRPC）、イベント駆動の3つが代表。どれも「誰が詰めて、誰が開けるか」を考える。
データベース

確認問題

答えを思い浮かべてから開いてください。

1. 「古いコードが、新しいコードの書いたデータを読める」のは、後方互換性と前方互換性のどちら？

前方互換性です。読む側のコードから見て、未来のデータを読めるからです。逆に、新しいコードが古いデータを読めるのが後方互換性です。

2. 前方互換性のほうが難しいのはなぜ？

古いコードは、あとで何が足されるかを知らないからです。知らない部分を無視できるように、最初から作っておく必要があります。そのうえ、読んで書き戻すときには、知らないフィールドを消さずに持ち続けなければなりません。

3. MessagePackが、テキストのJSONからあまり小さくならないのはなぜ？

スキーマを持たないので、フィールド名をデータの中に毎回入れるからです。例のレコードでは、66バイトのうち31バイトがフィールド名でした。Protocol BuffersやAvroはスキーマがあるので名前を入れずに済み、33バイトと32バイトになります。

4. Protocol Buffersで、変えてよいのはフィールドの名前とタグ番号のどちら？

名前は変えてかまいません。データに名前は入っていないからです。タグ番号は変えてはいけません。消したフィールドの番号を別の用途で使い回すのも禁止です。

5. Avroのデータには、フィールドを見分ける目印がない。ではどうやって読む？

書いたときのスキーマ（ライタースキーマ）を使って、順番どおりに切り分けます。そのあと、読むアプリのスキーマ（リーダースキーマ）と名前で対応づけて変換します。読み手にないフィールドは無視し、書き手にないフィールドはデフォルト値で埋めます。

6. 決済APIを呼んだらタイムアウトした。すぐリトライしてよい？

そのままでは危険です。リクエストは届いて処理も済み、返事だけが消えたのかもしれません。その場合、リトライで二重に課金されます。同じIDの依頼は1回しか実行しないしくみ（冪等性）があれば、安全にリトライできます。

7. 「データはコードより長生きする」とはどういうこと？ それで何が困る？

コードは数分で新しいバージョンに入れ替えられます。でもデータベースの中の値は、書き換えない限り、何年も前の形式のまま残ります。だから新しいコードは、いちばん古い形式のデータまで読めなければなりません。

8. メッセージブローカーを挟むと、直接のRPCより何がうれしい？

受け手が落ちていてもブローカーがためてくれます。落ちたプロセスには届け直してくれます。送り手は受け手の居場所を知らなくてよく、1つのメッセージを複数の受け手に配れます。送り手と受け手が切り離されるので、別々に変更しやすくなります。
